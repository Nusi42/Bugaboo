# ADR-0017: Background jobs stored in the database

Status: **Accepted** · 2026-10-04

## Context

Previews, virus scans, e-mail, webhooks, digests, backups, keep-and-delete runs and person removal need reliable background work.

## Decision

A small job queue in the database (`job` table with `run_at`, attempts, lease) run by `bb-jobs` inside the server process. Leases use `SELECT … FOR UPDATE SKIP LOCKED` on PostgreSQL and the single writer queue on SQLite. The jobs that come back every day repeat every 24 hours, fixed in the code (`bb_app::jobs::DAILY`); a schedule that people set (cron-like) becomes a setting in the registry when a job needs one (M9).

## Consequences

- Nothing extra to install; jobs survive restarts.
- Throughput is enough for the scale target; heavy work (previews) is limited by a worker pool size setting.

## Alternatives considered

- **Redis/RabbitMQ:** more installation and attack surface. Rejected.

## Enforced by

review; every job type has an idempotency test (part of ARCH-EVENTS test harness) (see `tools/checks/catalog.toml`).

## Amendment (M3 WP-08)

- **The runner exists (`bb-jobs`).** It depends on `bb-app` only (ARCH-DEPS): `spawn(services, every)` calls `Ctx::run_due_jobs()` on a timer, and `bb-server` starts it. The queue is behind the port `JobStore`; a round takes up to five due jobs under a lease of 120 seconds, runs each, reports it done (it leaves the queue) or failed, and a job that did a step queues the next one when more is left. A job that failed five starts goes to the dead-letter list.
- **Kinds so far:** `many-changes.step` (changing many issues: 100 issues in a step, progress kept in the table `change_run` after each issue, so a step that stops half way goes on at the next issue and no issue is changed twice) and `issues.renew-ids` (ADR-0021). `many-changes.step` judges again at run time what it does to each issue, with the permissions of the person who asked (`Ctx::acting`, `ctx_acting_as`). `issues.renew-ids` judges nothing: it finishes a change that was judged when the person changed the mode of IDs (they needed the right to change the project's settings then), so it renews the IDs of every issue of the project that does not have the new mode yet, and names that person on the events. Both are idempotent.
- **When a change is a job:** more than 1,000 issues (`MANY_CHANGES_JOB_ABOVE`); an access key may not start one (`auth.access-key-not-allowed`, M3-F121).
- **Jobs that come back every day.** `editing.purge-drafts` (drafts, notes for people who were editing and lock rows that ran out) and `history.catch-up` (the history reads the events, ADR-0007) are daily kinds; there is no timer of the server any more (M3-F30, M3-F71). `bb-server` calls `Ctx::start_daily_jobs` when it starts, which queues a round of each at once, and every round queues the next one a day later **before** it does its work, so a round that fails (the queue tries it again) or a worker that stops does not end the days. A round queues the next only when none for a later time waits (`JobStore::later_job_waits`), so a server that starts twice in a day leaves one chain of rounds, not two. Both are idempotent, and a read of a history still catches up first. The index of the text search (ADR-0016) and the notifications have no daily kind: every round of the jobs (`run_due_jobs`) catches them up, the first round after a start included.
- **Permissions are cached for one step.** A step of `many-changes.step` judges its (up to 100) issues with one context, which keeps what the policy engine decided for the person for the whole step (ADR-0025, decision 3: the cache lives as long as its context). A person who loses access while a run goes on is therefore stopped at the next step, not at the next issue: the next step builds a new context and judges from the roles they hold then, and the issues it leaves alone are named with `not-found` or `not-allowed`.
- **A stopped worker and the count.** The change to an issue and the saving of the progress of the run are two writes. The event of every change a run makes carries a reason that names the run and the item (`ManyChangeRun::item_reason`); a step that begins at an item whose event is there already (`ManyChangeStore::event_with_reason`, looked up by the range of event IDs since the run began) counts the issue as changed and goes on, instead of judging it again and reporting that it changed after the preview.
- **A tag or label counts the version.** Putting a tag or a label on an issue or taking one off counts the version of the issue up in the same change (by one, whatever the version stored then is: the routes do not take a version, so two people who add or take off different ones both succeed, and so does a tag put on while somebody saves the title; the event carries the version the row has after the count-up. The other way round, a save that read the version before the tag was put on is told that the version changed, like after any other change. An issue that went to the trash in between is not found), so a preview that read the version before sees that the issue changed in between and names it, also in a *Pick one* group where the label it would replace is not the one the issue has now.
- **One project event for the renewal.** `ChangeStore::record_changes` writes a change with any number of events of its own, also none. A step of `issues.renew-ids` writes the events of the issues it renews; the step that renews the last also writes the one event of the project (`issue-ids`).

## Amendment (M4 WP-05)

- **Kinds of files.** `files.preview` makes the preview of one attachment (the payload names the attachment, not the file): every attachment has a job of its own, also one of a file that is stored already, which takes an existing preview of the same content only when it runs. It is not daily. `files.clean-up` is a daily job: unfinished uploads a day after their last part, attachments after their 30 days in the trash, and files that nothing points to. Both are idempotent, and a preview job that failed for good ends the attachment (and the file, while nobody made a preview) as *without* a preview.

## Amendment (M5, nightly speed runs)

- **Statistics of the database.** `statistics.refresh` is a daily job, queued at every start like the others: on SQLite it runs SQLite's own `ANALYZE` of each table that SQLite reports out of date (it has rows and no statistics yet, or grew or shrank tenfold), one table at a time, and writes an empty table down as empty; otherwise it does nothing. PostgreSQL keeps its own statistics, and the job does nothing there. It writes no event: it changes no data. Idempotent: a second round finds nothing out of date (`adr_0017_the_statistics_job_writes_no_event_and_its_next_round_does_nothing`, both databases).

## Amendment (M6, time and working hours)

- **Kinds of M6** ([ADR-0035](0035-time-on-issues-and-working-hours.md)):
  - No job deletes working hours: after the keep period an administrator deletes them (ADR-0035, decision 7). The daily kind `working-hours.delete-old` of the first plan was dropped by the maintainer's decision, and no job counts the old days either: the settings page counts them when it is read.
  - `timers.long-running` is not daily: it is queued once for each timer, when the timer starts, for its start plus the longest day of the working-time rules (ADR-0035, decision 3). It marks the timer and queues the one notification; a timer that was stopped, switched or thrown away before then leaves it nothing to do, and a timer that was already marked is not told twice. A *Change start time* queues the job of the new start; the job of the old start finds a start that differs from its payload and does nothing.
- **The statistics keep away from the start (M5-F168).** `statistics.refresh` is not in the round that `Ctx::start_daily_jobs` queues at a start: its round of a start is queued `QUIET_KIND_AFTER_START` (5 minutes) later, and every round after that at `QUIET_HOUR` (03:00) of the time zone the organization chose under *Region* (UTC when it chose none). The one schedule of the daily jobs is the rhythm of each kind (`JobKind::rhythm` in `bb_app::jobs`): `FromTheStart` (at every start, then every `DAILY`) for every other kind, `QuietHour` for the statistics; a match without a catch-all, so a new kind has to say. A round queues the next only when none for a later time waits, as before, so a start within the day leaves one chain (`adr_0017_the_start_round_queues_no_statistics_refresh`).
- **A write that meets the upkeep is tried again.** While `Database::refresh_statistics` runs it marks the upkeep (`db/upkeep.rs` in `bb-store`). A write that meets SQLite's busy answer meanwhile, after the busy timeout every writer has (`SQLITE_BUSY_TIMEOUT`, unchanged), is tried again, `BUSY_WRITE_TRIES` times in all with `BUSY_WRITE_WAIT` between. Only what can be tried again whole is: the start of a transaction (`BEGIN IMMEDIATE` takes the lock before anything is written) and a statement on its own (`Database::execute`, its own transaction), so a try that met the busy answer changed nothing and a change, its event and its entry of the outbox are written once. The loop is the one for a locked database, which also opens a new file (`while_locked`). A write that stays busy after its last try is `StoreError::Busy`, which the use cases answer with the plain refusal `server.unavailable` (*Bugaboo is not available right now. Please try again in a moment.*, `internal` in `bb_app::auth::error`, the one place a failure of the store becomes an answer); a job that meets it is tried again later like any failure of the store, and a step of a change to many issues fails and is tried again instead of naming the issue as not valid. PostgreSQL has no lock of the whole database and never tries again (`adr_0017_a_write_during_the_statistics_refresh_is_tried_again_and_lands`, `adr_0017_a_write_that_stays_busy_is_refused_in_plain_words_after_the_last_try`, both databases).

## Amendment (M7, agents and AI apps)

- **Kinds of M7** ([ADR-0029](0029-ai-agents.md), [ADR-0042](0042-mcp-server-and-how-ai-apps-sign-in.md)), each idempotent:
  - `agents.hand-over-runs-out` is not daily: it is queued once for each hand-over, for its end (ADR-0029, decision 3). It ends a hand-over that is still open (its work becomes *Stopped*); a hand-over that ended before, or whose end was moved, leaves it nothing to do (the job of a moved end is queued anew, like `timers.long-running`).
  - `agents.rule-runs-out` is not daily: it is queued once for each standing rule, for its end (ADR-0029, decision 3). It ends a rule that was not renewed; *Renew* queues the job of the new end, and the job of the old end finds an end that differs from its payload and does nothing.
  - `agents.rule-about-to-run-out` is not daily: it is queued with the rule, for 3 days before its end, and queues the notification *A standing rule runs out soon* (ADR-0033, amendment M7) unless the rule was renewed or ended.
  - `agents.rules-get-an-end` is not daily: queued in the change that switches the setting *Allow rules that never run out* off. It gives each standing rule that never runs out an end at the most days (90) from then, with the usual end and warning jobs, and does nothing when the setting is on again (ADR-0029, amendment M7, WP-14).
  - `agents.rule-matches` is not daily: the outbox queues it after an event that changes an issue in a project where a standing rule works, at most one waiting for each rule. It writes down each issue that newly comes under the rule, with the moment, once (ADR-0029, decision 3).
  - `oauth.clean-old-grants` is daily (`FromTheStart`): it deletes authorization codes and refresh tokens that ran out, and grants that were taken back or ended, as ADR-0042, decision 3, says; a grant in use is never touched, nor one waiting while AI apps are switched off (ADR-0042, decision 4).
- **Who a job of agents acts as.** A job that ends or records something for an agent judges nothing new: it finishes what the person decided when they handed over or made the rule, and names the agent and its person on the events. A match is written down only for an issue the agent may read at that moment (ADR-0029, decision 2).

## Amendment (M8, work times)

- **Kinds of M8** ([ADR-0030](0030-planning-with-people.md), amendment M8), each idempotent:
  - `work-times.delete-old-away-times` is daily (`FromTheStart`): it deletes every away time whose last day is more than one year ago (`AWAY_TIME_KEPT_FOR`), with its note, and also the events of away times that were removed, one year after the event.
  - A person who leaves the organization loses all their work times in the step that ends their membership, not in a job: one function of the module of work times, which *Remove a person* calls (M9). In M8 it is built and tested on its own.
- **No job deletes shares.** The share of a person who no longer has a role in a project counts as nothing and is kept until the person leaves (ADR-0030, amendment M8): business data is deleted only explicitly.
- **Nothing else of M8 is a job.** The plan is worked out when it is asked for (ADR-0030, amendment M8), and the public holidays are computed, never fetched.

## Amendment (M9, *Download my data*)

- **Kinds of M9** ([ADR-0044](0044-download-my-data-and-remove-a-person.md), decision 2), each idempotent:
  - `privacy.export` is not daily: it is queued in the change that asks for an export and writes its file through the walk of the person's data. An export that waits no more leaves it nothing to do; a try that fails leaves the export waiting for the next. Each try writes a file of its own and keeps its lease while it works, renewing it when half of it has passed (a file can take longer than any fixed lease); the change that marks the export ready makes that try's file the export's, and it changes nothing, with no event and no notice, when another try finished the export first. When the job gives up, the export becomes *Failed*, so the person may ask again, and what was written of its file is deleted.
  - `privacy.delete-old-exports` is daily (`FromTheStart`): it deletes the exports past the keep period of the row *Data exports* of the keep and delete rules (ADR-0045; 7 days, `EXPORT_KEPT_DAYS`), through the one deleting step `keep_step`: at most `KEEP_STEP_ROWS` exports a step, the file first, then its record with an event, and the next step queued after the pause `KEEP_STEP_PAUSE` when a step was full; a file that is gone already is no error.
  - `privacy.finish-removal` is not daily: it is queued in the change that removes a person, with the comments, issues and exports that change deleted, and finishes it in steps: the files of the exports go, the rows of the deleted comments leave the full-text index and the rows of their issues are made again, at most 500 issues a step, each step queueing the next. After the last step SQLite merges the segments of the index (FTS5 `optimize`, which holds the write lock for the whole merge, so other writes wait for it and a large index makes them wait longer) and empties the write-ahead log (`wal_checkpoint(TRUNCATE)`); every SQLite connection runs with `secure_delete` on, so the pages a delete frees hold zeros (M5-F52). PostgreSQL has no such step: its own vacuum takes back the space. Each step is safe to run again; a job that gives up is written to the server log and keeps its payload on the dead-letter list.

## Amendment (M9, keep and delete rules)

- **One shape of deleting by itself** ([ADR-0045](0045-keep-and-delete-rules.md), decision 5). Every daily kind that deletes what outlived its keep period runs through `Ctx::keep_step` (`bb_app::keeping`): a round is one step, each part of it deletes at most `KEEP_STEP_ROWS` (100) rows in one short write (the store chooses them with `keeping::limited_rows`, which both databases understand), and a part that reached its limit queues the next step of the same kind after `KEEP_STEP_PAUSE` (3 s), so a large backlog (the first run after an upgrade or an import) is worked off beside the writes of people, not ahead of them: on the sample organization a thousand old notifications held SQLite's write lock for 70 to 250 ms, and steps queued at once kept ten people writing comments above their budget of 100 ms. The next daily round waits already, so a step adds no second chain. `JobKind::keeps` names the rows of `bb_core::keeping::KEEP_KINDS` each kind deletes; a row of the group *by an administrator* has no kind (`priv_05_every_kind_of_data_has_one_row_and_one_group`). The kinds `notifications.purge`, `security-log.prune`, `sessions.purge`, `editing.purge-drafts`, `files.clean-up`, `work-times.delete-old-away-times` and `oauth.clean-old-grants` keep their names; the loops of rounds of `files.clean-up` are gone. `server-log.rotate` keeps a number of files, not a period, and has no row.
- **New kind** `jobs.purge-dead`, daily: deletes the jobs on the dead-letter list whose last start is longer ago than `keeping.dead-job-days`, with their payload (M1-F21). `notifications.purge` no longer empties payloads.
- **The quiet hour** is the rhythm of `security-log.prune` and `jobs.purge-dead` too, beside `statistics.refresh`; the rest keep `FromTheStart`.
- **Periods from the settings.** The periods of notifications, the trash, dead jobs and IP addresses are settings of the registry (`settings::keeping`), read by the jobs; the constants `notification::KEEP_DAYS` and `job::DEAD_PAYLOAD_KEEP_DAYS` are gone.
- **`sessions.purge` forgets IP addresses.** It also empties the shortened network address of every session older than `keeping.ip-address-days`.
