# ADR-0047: Releases: signatures, the parts list, the support period and vulnerability handling

Status: **Accepted** · 2026-11-18 · refines SEC-18, COMP-01, COMP-03, COMP-04, DIST-07 and [ADR-0040](0040-version-numbers.md); the answers to M9-Q12 to M9-Q14 and M9-Q16 of [the M9 plan](../milestones/M9/README.md)

## Context

M9 ends with the first release of Bugaboo that people can install and run for real. The Cyber Resilience Act asks a manufacturer for a software bill of materials, a way to report vulnerabilities, advisories, reports of actively exploited vulnerabilities within 24 and 72 hours (in force since 11 September 2026), free security updates for a declared support period, and secure defaults (compliance.md §1). The new Product Liability Directive covers software placed on the market from 9 December 2026. Bugaboo is free, AGPL-licensed, and nothing commercial is offered until a lawyer has reviewed it (ADR-0036, decision 5).

Today the repository has lockfiles, the register of direct dependencies, the license allow list and the advisory scan (DEP-REGISTER, DEP-LICENSES, SEC-ADVISORIES), `SECURITY.md` with private reporting on GitHub, and `cargo xtask build`, which builds the Windows program. DEP-SBOM is planned and not built. Nothing is signed. There is no certificate for Windows code signing on this computer, no hosted build (ADR-0037), and the static Linux program is built only on Linux.

## Decision

1. **What a release is.** A release is a tag `vX.Y.Z` on `main`, the version of ADR-0040 (M9 brings 0.6.0). `cargo xtask release` builds it on the development PC and in WSL and writes one folder: the programs (decision 7), `SHA256SUMS`, a signature for each file, the parts list (decision 3), the third-party notices, the release notes and known issues. The maintainer publishes that folder as a GitHub release and as the files a served instance is updated from. Enforced by: DEP-SBOM, review (the maintainer publishes).
2. **Signatures with our own key** (M9-Q12). Every file of a release, the checksum list and the parts list are signed with one Ed25519 release key in the `minisign` format, so anybody can check them with that common tool or with `bugaboo update verify <file>`, which knows the public key. The public keys are written once, as a list (`bb-core::release::RELEASE_PUBLIC_KEYS`): the release key and a backup key that the maintainer keeps apart, so a lost or leaked key can be replaced by a release signed with the other; the rotation is a written step of the release guide. They are copied into `SECURITY.md` and the release page by the build. The program verifies with `minisign-verify`; xtask signs with `minisign`; both get their register rows. The private key never enters the repository or a work folder: the person who signs keeps it safe and signs with `cargo xtask release sign`. Tests sign with a key made for the test. Windows code signing (Authenticode) waits for a certificate the maintainer decides on; until then Windows warns about an unknown publisher, and the install guide says how to check the signature first. Enforced by: SEC-SECRETS (no key in the repository), review (the signing step reads the key from outside the work folder).
3. **The parts list** (SBOM; decided by the rules: one source, no new tool). `cargo xtask release` writes it in CycloneDX 1.6 JSON and SPDX 2.3 JSON from the lockfiles (single source, coding-standards §1): every crate that is compiled into each program (the dependency tree of the target, without build-only and test-only crates), every npm package bundled into the browser app, and the texts of `docs/third-party/notices/`, each with version, license and checksum. Bugaboo bundles no font files (it uses the system font stacks); the Lucide icons (ISC) are listed as the package or files they come from. xtask writes both formats itself from `cargo metadata` and `package-lock.json`; no new tool is installed; a test-only JSON schema validator of xtask checks both files. The program carries the parts list and the notices of its own build, so *About* shows them. Enforced by: DEP-SBOM (made, complete against the lockfiles, valid against both schemas), DEP-REGISTER, DEP-LICENSES.
4. **Vulnerability handling.**
   - `SECURITY.md` says which versions get fixes (decision 5), how to report (GitHub's private reporting), the answer within one week, coordinated disclosure within 90 days, and that we report actively exploited vulnerabilities and severe incidents through ENISA's single reporting platform within 24 hours (early warning), 72 hours (notification) and the final report.
   - The runbook `docs/security/vulnerability-runbook.md` lists the steps from report to advisory, with the CRA deadlines; the full incident runbook for us as manufacturer and operator is DIST-08 (V1).
   - Every advisory that is accepted in `deny.toml` or `tools/checks/npm-advisories.toml` gets a VEX statement in the release folder (CycloneDX VEX: *not affected* and why), written from the same entries and the register's *Accepted risks*, so the reason is written once (M6-F126).
   - Bugaboo serves `/.well-known/security.txt` (RFC 9116, M9-Q16): our contact first, the organization's own contact when an administrator sets one, and an expiry one year after the release, so an old installation shows its age.

   Enforced by: SEC-ADVISORIES, DEP-SBOM, SEC-HEADERS, review (the runbook is read before each release).
5. **The support period** (M9-Q13). Until 1.0, every release is a free public preview: only the newest release gets fixes, and a fix comes as the next patch release (0.6.1). From 1.0 on, each minor release gets security fixes for 5 years from its date, declared on the release page and in *About*. Security fixes ship as patch releases made from the release's tag on a branch `release-X.Y`, without new features. Enforced by: review (the release notes name the support period).
6. **Secure by default** (COMP-04). The settings that matter for security start safe and a test lists them: HTTPS on, sign-up off, every kind of AI off, e-mail off, outside images blocked, two-step sign-in offered, the data folder owner-only. `docs/security/cra-requirements.md` maps each essential requirement of the CRA (Annex I) to the features, checks and tests that meet it. Enforced by: ARCH-SETTINGS, SEC-HEADERS, review (the mapping is read before each release).
7. **Platforms of the first release** (decided by the rules): Windows x64 and Linux x64 (static, for any distribution and WSL). Windows ARM64 waits for the ARM64 build tools (M1-F01), Linux ARM64 for a cross linker; both join a later release without a change to the code. Enforced by: review (the release folder lists its platforms).
8. **Updates** (DIST-07; M9-Q14). A self-hosted installation is updated by replacing the program after the *installed* program's `bugaboo update verify <new file>` has checked the new file's signature and warned when the version in its trusted comment is older than its own (a downgrade); the next start backs up and migrates (ADR-0046). The update notice inside Bugaboo and its signed check of the feed are OPS-11 (V1, M14). Served instances are updated by us with the same signed files, in announced maintenance windows, from M14 (DIST-02). Enforced by: review (the install guide and the release notes describe the update).

## Consequences

- A release needs the maintainer twice: to sign with the release key, and to publish.
- A person on Windows sees a warning about an unknown publisher until a code-signing certificate is bought (M9-Q12).
- The parts list is checked in every full run, not only at release time, so a release never finds a gap late.

## Amendment (M9, the parts list)

- **The schema validator is a normal dependency of xtask, not a development-only one.** Decision 3 said "test-only". The check DEP-SBOM runs inside the xtask program in every full run and must validate both files, so the validator (`jsonschema`, built without its network code) is compiled into xtask. It is never part of the program that ships, and its register row says so. Enforced by: DEP-REGISTER.
- **The crate list is what `cargo tree -e normal` says each program compiles in.** `cargo metadata` joins the features of every member of the workspace, so it names crates that a program does not compile in; it still gives the licenses and the edges. DEP-SBOM holds the list to `cargo tree` in both directions, and the npm packages to the lockfile's own marks (not `dev`, not `devOptional`). Enforced by: DEP-SBOM.
- **A crate without a license file** gets the standard text of its declared license in the notices (decision 3), with the authors named in the package as the copyright holders.
- **The VEX reason is the register's.** A statement takes its reason and its CycloneDX justification from the row of the register's *Accepted risks*; an accepted advisory without a row, or with a justification CycloneDX does not know, fails DEP-SBOM. Enforced by: DEP-SBOM.
- **The files are the same bytes only for the same lockfiles and the same installed packages:** the license texts are read from the installed crates and packages.

## Amendment (M9, signed releases and the support period)

- **The trusted comment** of every signature is `file:<name>` and `version:<version>`, separated by a tab like the comments of the minisign tool (`bb_core::release::TrustedComment`, one writer and one reader). Only signatures of the file's hash (the minisign default) are taken. `bugaboo update verify` checks the file's signature, the signature of `SHA256SUMS` beside it, and the file's checksum in that list under the name its signature gives, so a download saved under another name is still found. Enforced by: review (`sec_18_…`, `dist_07_…`).
- **Where the support period lives.** `[workspace.metadata.release]` of `Cargo.toml` holds the day of the release and the years of support from 1.0; `bb_core::release` reads it at compile time, so a missing or malformed entry stops the build. A preview (0.x) answers `fixes_until: null` in *About*. `security.txt` expires one year after that day. Enforced by: review (`comp_04_about_answers_the_support_period_from_its_one_home`).
- **Test keys until the real ones.** `RELEASE_PUBLIC_KEYS` holds two test keys whose secret keys were thrown away, and `KEYS_ARE_FOR_TESTS` is `true`; `SECURITY.md` and the notes say so. The change that puts the real keys in sets it to `false`. Enforced by: DOC-GENERATED (`SECURITY.md` follows the code).
- **The organization's contact** (`security.contact`) is taken only as one `https://` address or e-mail address (made into `mailto:`): anything else is refused when it is saved, with a sentence that says what to write, and left out of `security.txt` should a database hold it, so a value can never add a field. Enforced by: review (`comp_03_…`).
- **The secure defaults** (decision 6) are one table in the test `comp_04_every_setting_that_matters_for_security_starts_safe`. Every setting of sign-in, security, AI, AI apps, agents, the assistant, e-mail, content and files is judged there: it is in the table with its starting value, or in a list of settings that do not matter for security, with the reason; a new one fails the test until it is in one of them. **Every kind of AI starts off:** the assistant, AI apps and agents (`ai-apps.enabled` and `agents.enabled` start off; this replaces the *on* of ADR-0029 and ADR-0042). A stored value is only a change of the default, so the change alone would switch both off in every installation that never touched them: migration 59 writes *on* as the organization's own value where a person already exists and the organization set no value, so an upgrade keeps AI apps and agents as they were, and a new installation, which migrates before setup makes the first person, starts with both off. Enforced by: ARCH-SETTINGS, the tests `comp_04_…` of migration 59 on both databases, review.
- **The release name of a test build.** A folder built without its tag on the commit, or while `KEYS_ARE_FOR_TESTS` is `true`, is named `<version>-test`, and so is every file in it and the version in every trusted comment, so a signed test file never passes for a release. Once the real keys are in, `release sign` refuses a folder built without its tag and a key that is not in `RELEASE_PUBLIC_KEYS`, and `cargo xtask release` refuses a day of the release that is not the day of the tag's commit. `release check` names a file in the folder that does not belong there. `bugaboo update verify` takes `SHA256SUMS` only when its signature names `file:SHA256SUMS` and the same version as the file. Enforced by: review (`sec_18_…`).
- **The support period counts from `X.Y.0`** (decision 5): `[workspace.metadata.release]` holds `minor-date`, the day of the first release of the minor version, beside `date`; a patch release never adds time. Enforced by: review (`comp_04_a_patch_release_is_supported_from_the_day_of_its_minor_release`).

## Amendment (2026-11-21, keys without a passphrase)

- **The two keys have no passphrase** (this replaces the passphrase of decision 2). `cargo xtask release keygen --out <path>` writes an unencrypted minisign key pair and asks nothing; `cargo xtask release sign` opens such a key without a question. An older key with a passphrase still opens, and only then is the passphrase asked for on the console. Both commands still refuse a place inside the repository or any work folder, and `keygen` never writes over a key.
- **Keeping the keys.** The person who signs keeps the release key and the backup key apart from each other and safe. A key that is lost or may be known to somebody else is replaced through the other one, as the release guide's step *Replace a key* says.
- **The secret key file is its owner's alone.** `keygen` makes it so before anything goes into it: mode `0600` on Linux; on Windows an access list with only the owner and nothing inherited, set with `icacls` as the server sets the files of its data folder. `sign` refuses a key file that the group or everybody (Linux), or everybody, all users or all signed-in accounts (Windows) may read, and a file whose rights it cannot read, with the command that closes it. Only a key whose KDF field says it has a passphrase is opened with one; any other is read as a plain key, so a damaged key is an error and never a question.
- Enforced by: review (`sec_18_keygen_writes_a_key_without_a_passphrase_that_signs_without_asking`, `sec_18_an_older_key_with_a_passphrase_still_opens_with_it`, `sec_18_the_secret_key_is_its_owner_s_alone`, `sec_18_a_damaged_key_without_a_passphrase_is_an_error_and_never_a_question`, `sec_18_signing_refuses_a_key_inside_the_repository_or_a_work_folder`, `sec_18_a_key_folder_behind_a_link_is_taken`).

## Alternatives considered

- **Sigstore (cosign keyless):** needs a hosted build identity and the network at signing time; ADR-0037 has no hosted build. Not now.
- **GPG signatures:** heavier for people to check, with key servers and trust models. Rejected in favour of minisign's single public key.
- **`cargo cyclonedx` and `@cyclonedx/cyclonedx-npm`:** two more pinned tools that each cover half and still need merging; SPDX needs a third. Rejected.
- **5 years of support for 0.x:** a promise a single maintainer cannot keep for previews, and a preview is not placed on the market commercially. Rejected until 1.0.

## Enforced by

DEP-SBOM, DEP-REGISTER, DEP-LICENSES, SEC-ADVISORIES, SEC-SECRETS, SEC-HEADERS, ARCH-SETTINGS; review (signing, publishing and the runbook are steps of the maintainer).
