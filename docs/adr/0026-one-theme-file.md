# ADR-0026: One theme file for everything about how the app looks

Status: **Accepted** · 2026-10-08 · replaces the styling part of [ADR-0010](0010-design-tokens.md) · updated in M6: a base file and one file of colors and its shadow per theme (decision M6-Q1) · updated in M8: themes of your own (M8-Q8 to Q11)

## Context

Requirement (M2C): **all UI theming lives in one theming file**, the way a sister project keeps its complete look in one theme file. ADR-0010 made `design/tokens.json` the source of colors, fonts, sizes, radii and shadows, but let every component keep its own CSS Module. The audit of M2C (section D) found what that costs:

- 55 CSS modules with 3,261 lines; values that have no token (`font-weight: 700` 57 times, line heights 38 times, about 50 `1px solid` borders, a z-index chosen per file, opacities, keyframes);
- the same rule copied into many modules (the focus ring 22 times, the muted text, `.stack`, `.row`), the skip link twice, and `forced-colors` handling in ten components;
- the theme list written in `tokens.json` and again in the settings registry in Rust, held together by a test (M2C-F64);
- theme names and the `data-look` attribute written by hand in TypeScript and in the browser tests.

The sister project compiles its theme to CSS **in the browser** and injects it as a style element. Bugaboo cannot do that: the content security policy is `style-src 'self'` (SEC-11), so nothing may put a style on the page at run time.

## Decision

1. **One file, `design/theme.kdl`** (KDL, decision M2C-Q1). It holds everything: the themes, the choices that change token values, every token with its variants per mode, the contrast rules, the mixins, the keyframes and the rules of every component. Comments are allowed, and each token is one line. It replaces `design/tokens.json`. Only `cargo xtask gen theme` reads it (with the `kdl` crate, pinned like the sister project's); the server and the browser never parse KDL.
2. **Values are tokens, with their variants per mode on the line of the token.** A token has a kind (`color`, `font`, `size`, `number`, `duration`, `easing`, `shadow`, `weight`, `line-height`, `border-width`, `layer`, `opacity`) and, besides its value:
   - `<theme>=` for each of the four themes (colors and shadows), with `kind="light"` or `"dark"` on the theme;
   - `<theme>-more=` for a device that asks for more contrast (`prefers-contrast: more`);
   - `forced=` while forced colors are on (`forced-colors: active`);
   - `<choice>=` while a choice of the person is on: `compact` spacing, `larger-text`, `less-motion` (which the device can switch on too).

   Every token of ADR-0010 keeps its value; the file adds font weight, line height, border width, layers (z-index), opacity, easing, the brightness of a pressed primary button, and forced colors as a mode. The focus ring is two tokens (`ring-width`, `ring-offset`) and one mixin (`ring`) that every rule `use`s.
3. **Rules are `part` rules that use tokens only.** `part "button[variant=primary]:hover" { background "$accent" }` styles every element that says `data-part="button"` and `data-variant="primary"`. A value is a word, `0`, a percentage, or `$token` (written `var(--token)` in the output); a length, color, duration, weight, line height, layer or opacity written out is a finding of LINT-CSS and STY-TOKENS. `base` rules style the page frame (`html`, `body`); `mixin`, `keyframes` and `forced { … }`, `more-contrast { … }`, `media "…" { … }` blocks complete the language.
4. **Components carry no style values and no class names.** They emit `data-part`, `data-state` and `data-variant`, through `partOf(part.button, { variants: […], states: […] })` of `@bugaboo/ui`. The names of the parts and the words a part may have (`partWords`) are generated into `tokens.ts` from the rules, so a misspelled part or word is a type error. React Aria's own `data-*` state attributes (`data-hovered`, `data-pressed`, `data-selected`, `data-focus-visible`, `data-entering`, …) are allowed and used: a rule names them as `button[hovered]`.
5. **The file is compiled at build time into one static style sheet**, `web/packages/ui/src/theme.css` (committed, with a copy for the design pages at `docs/design/theme.css`). The content security policy stays `style-src 'self'`; no style element or attribute is made at run time. This is where Bugaboo differs from the sister project. Neither file is edited by hand: DOC-GENERATED compares them with the output of `cargo xtask gen theme`.
6. **The list of themes is written once.** The four built-in themes (Daylight, Paper, Dusk, Midnight) and the two that start are defined in the file. `gen theme` writes them to TypeScript (`tokens.ts`: `themeIds`, `lightThemeIds`, `darkThemeIds`, the defaults) and to Rust (`crates/bb-core/src/settings/themes.rs`: the choices of the settings *Light theme* and *Dark theme* and their defaults, which `catalog.rs` names). The reader of the settings registry follows those names, so the browser's generated choices and defaults come from the same file. There is no hand-kept list in `catalog.rs` and no test that holds two lists together (closes M2C-F64).
7. **Custom themes, later, store token values only**: names from the generated token list, values checked by the kind of the token. They never add a rule, a selector or CSS text. How the values reach the page without breaking the policy is decided when the theme editor is built.
8. **Contrast is checked per theme and per mode** (STY-CONTRAST), the way the sister project's contrast check does: every text color on every background in each theme, and with `<theme>-more=` the 7:1 and 3:1 rules of ADR-0010. The rules for it are the `contrast` and `distinct` lines of the same file: `hovered` (the pair of a brightened main button as it is seen hovered), `stronger` (the quiet words of a row at 5:1 on the tints), `lines` (the edge of High, the hover line and the ring on the tints and surfaces) and `fills` (a fill that carries no text, the square of a label, held like a line at 3:1 on the surfaces, M5-F149) inside `contrast`; `distinct` also asks for a least difference of color (`min-delta-e-…`, CIE 1976 delta E) between the three status tints and the card, between the red of Critical and the orange of High, and between the squares of the twelve label colors, because a ratio only knows brightness. `dimmed` holds the page behind a sheet as it is drawn (the token `scrim` over the fill and the text of the page): the sheet stands out and the page text is dim. A `distinct` rule that names no minimum is a parse error.
   Bold is the same kind of rule: the file has one `bold` list that names the selectors that may set the bold weight, each with its role from UX §7.3 (STY-BOLD), so a bold that UX does not name cannot be added by accident.
9. **The design pages are generated too.** `docs/design/components.css`, `docpage.css`, `ux-design.css` and `mockup.css` style the documents and mockups in `docs/`, not the app (the last two hold what the UX page and the mockup had in a `<style>` block, and the classes that replaced their `style=` attributes). They are written in the same file as `docs` blocks: `rule` lines with plain CSS selectors (the pages use class names and elements, which parts must not) that use tokens only, and the tokens of the pages themselves (`doc-…`), which go to `docs/design/theme.css` and not to the app's sheet. `gen theme` writes both sheets, LINT-CSS reads them like the parts, and DOC-GENERATED compares them (M2C-F93, done in C-06). The motion of the pages follows the motion tokens, so there is no reduced-motion rule with `!important`. THEME-ONLY reads the pages of `docs/` too: no `<style>` element and no `style` attribute in the markup, unless the page's own script builds its value (a position or a color it computes, which is a style of the run time, M2C-F105).
10. **Moving was done in two steps.** M2C C-01 built the engine and moved the primitives of `packages/ui`. M2C C-06 moved every app feature, the shell and the other components (M2C-F90): there is no CSS Module, no `cx` and no exemption any more, and THEME-ONLY passes with nothing exempt. What several features said the same way is one part (`stack`, `text`, `muted`, `row`, `list`, `item`, `facts`, `hint`, …, M2C-F65), and the focus ring, the skip link and the forced-colors outline of the marked item (`marked`) are written once.
11. **The names of the page frame are written once.** The attributes of `<html>` that the sheets and the code use (`data-look`, `data-theme`, `data-preview-look`) are the `frame` line of the file. `gen theme` writes them to the sheets, to `tokens.ts` (`pageAttributes`), which `theme.ts`, the theme sample and the end-to-end specs read, and to `docs/design/frame.js` (`bugabooFrame`), which the scripts of the design pages read (M2C-F91). The choices (`data-spacing`, `data-text`, `data-motion`) are read from `variants` the same way.

## Update (M3 WP-16, the new look)

- **Choices of the device.** A `variant` may have only `media=` (no attribute on the page): `touch` (`(pointer: coarse), (width < $bp-tablet)`) gives a token its finger value (`size-control` 36 becomes 44, `size-row` 44 becomes 64), `phone` gives text 16. A media query may name a `$token` with a plain value.
- **Container queries.** A rule may hold `container "(min-width: $bp-window-side)" { … }`, written as `@container`: a window follows its own width, not the screen's (UX §6.3).
- **Feature queries.** A rule may hold `supports "(width: calc(1px * (2px / 1px)))" { … }`, written as `@supports`: a line that needs a newer browser is read only by a browser that has it, so the line before it stays where it does not. Variables inside a media block are no such guard: a browser that cannot compute them drops the line to its start value, not to the line before.
- **One run-time style.** The size a person drags a window to is two variables of the theme file (`window-width`, `window-height`). The issue list adds four, for the same reason (a size the browser measures or the person drags, which no token can hold): `list-columns`, the widths of the columns that the head and every row share; `list-gutter`, the width of the scroll bar the rows have now, so the head keeps the same room and the columns stand over each other; and `list-width`, the width of the head as the browser measured it (as wide as its columns need), which is given to the virtualized rows because they have no width of their own, so head and rows scroll sideways as one; and `size-code-char`, one character of the code font as the browser draws it, measured from a probe in that font (the font of the computer may be any of its stack), so the ID column is as wide as the IDs really are. THEME-ONLY allows exactly `element.style.setProperty(variableOf("…"), value)`: `variableOf` only takes the name of a token, and nothing else may set a style from code.
- **The pictures use the parts.** `cargo xtask gen theme` also writes `docs/design/parts.css`, the rules of the parts without the tokens, so the pictures of the UX design are drawn with the same `data-part` markup as the app and cannot differ from it.
- **Several `distinct` rules.** The hovered and the selected row must differ from the tint of a status group as well as from the plain surfaces, so the file has one `distinct` rule for the plain surfaces and one for each tint.

## Update (fonts like the sister project)

- **System font stacks, no font files.** Decision: Bugaboo handles fonts like its sister project: the theme file has the sister project's four stacks word for word, and Bugaboo ships no font file, has no `@font-face` and asks no font service. The reasons: one look across the sister projects; nothing to download before the first page draws; no font licence to carry in the dependency register. A computer without the named faces takes its own system face (the last word of each stack), so text may look a little different between systems.
- **One token per role, the sister project's roles.** `font-ui` is the text of the app (rows, fields, buttons, menus); `font-display` the titles and section headings, that is the parts the `bold` list names with the roles `issue-title`, `title` and `section` (STY-BOLD finds a rule of such a part that makes it bold without the display face); `font-reader` what a person reads at length (a description, a comment, the help of the search); `font-mono` code, issue IDs, the search language and time values. Every rule that sets a family names one of the four.
- **Cascadia Mono is first for code.** Its regular weight draws with about a third more ink than the text face (M5 exit F-A1 measured 491 against 367 units for one line of 14 px), so code and IDs read a little heavier than the words around them. This is accepted to keep the sister project's stack exactly; STY-BOLD no longer refuses a font by its name, and it still refuses any bold weight the `bold` list does not name.
- **Measured, not assumed.** The width of the ID column still comes from `size-code-char`, a probe drawn in the code font of the computer, so it is right for Cascadia Mono, Consolas or the system monospace face alike.

## Update (M6, theme files like the sister project)

Decision of the maintainer (M6-Q1, M5-F167, M5-F121): the themes are handled the way the sister project handles them. Decisions 1, 2 and 6 read as follows; the rest stands.

- **A base and one file per theme.** `design/theme.kdl` is the base theme, `default`: `defaults`, `frame`, `variants`, every token with its value and its `more=`, `forced=` and choice values, the `contrast`, `distinct` and `bold` rules, the mixins, keyframes, part rules and `docs` blocks. Its colors are those of Daylight, the light theme that starts. Each built-in theme is a file of `design/themes/`:

  ```kdl
  theme "dusk" extends="default" kind="dark" {
      tokens {
          color "bg-canvas" "#1d2027"
          color "border" "#3b414d" more="#999ca2"
      }
  }
  ```

  A theme file sets **only the colors it changes** (`more=` is its color for a device that asks for more contrast), so no value is written twice: Daylight's file is empty, and a theme that sets no color looks like Daylight. A line of a theme replaces the base's color and its `more=` together; a color the theme does not set keeps both from the base. A `more=` that is the color itself says nothing and is refused. With more contrast, a theme's block says again every color that the dark theme that starts changes there (the dark fallback of the device weighs as much as the theme's own block and comes after the theme's usual block, so a color its more-contrast block left out would be Dusk's), so a theme never shows Dusk's color for more contrast. `forced=` and the choices stay on the line of the base.
- **The file name is the theme's ID** (`dusk.kdl` is the theme `dusk`, and the file says `theme "dusk"` so that it reads on its own; the reader refuses a file whose two names differ). The list of themes is the list of files: there is no `themes` block. The files are read in name order and listed light themes first, each kind in name order, which is the order of `themeIds` in `tokens.ts`, of the choices in `themes.rs` and of the blocks of the sheet. A new built-in theme is one new file (and its name in the message catalog); `tokens.ts` and `themes.rs` follow without any other change.
- **A token may name another token** (M5-F121): `color "hover-line" "$border-control"`. The sheet keeps the link as `var(--border-control)`, so the browser follows it in every theme and mode; a theme file may give the token a color of its own (the dark themes give the hover line a brighter one) or name a source as well (Midnight's `st-ns` names `fg-muted` and has its own `more=`). STY-CONTRAST reads the color the link leads to, in each theme and mode; a link to a name that is no color token, and a loop, are errors of `gen theme`.
- **Shadows are the one other kind a theme sets.** Today the shadow of a raised surface differs in shape between the themes (a ring in Midnight, a deeper drop in the dark themes), not only in color, so a theme file may set a `shadow` as well as a `color`. The maintainer accepted that a theme file sets its shadow as well as its colors (one shape for all four would have changed the look of Dusk and Midnight, and the split was to change nothing on screen). Whether the themes share one shape stays a question for the theme editor (M8). A theme file that sets any other kind of token, names a token the base does not have, sets a token twice or extends anything but `default` is an error of `gen theme` that names the file and the line.
- **One reader.** Only `cargo xtask gen theme` reads the files (`ThemeFile::load` in `xtask`); the tests of the pictures of the front page read the colors from the generated sheet, not from KDL. The content security policy stays `style-src 'self'`: the files are compiled at build time into the one static sheet, as decision 5 says.
- **Checks.** STY-CONTRAST runs for every theme file and mode and names the theme's file in a finding; LINT-CSS and STY-TOKENS run again when a theme file changes; DOC-GENERATED compares the output of the base and the theme files.

## Update (M8, themes of your own)

The maintainer's answers M8-Q8 to Q11 (2026-11-11). They settle decision 7 and leave the others as they are. The words are the glossary's: an *own theme* is a theme an organization or a person makes, *for everyone* or *personal*.

- **What an own theme may set** (M8-Q10). The colours (each `color` token, with its `more=` colour), the shadow (the `shadow` token that a theme file may set, stored as its parts: offsets, blur, spread and a colour, at most two layers, never as text), the corner radius (`r-ctl` and `r-card`, within the bounds the base file gives them), and for the text faces `font-ui`, `font-display` and `font-reader` a choice among the system font stacks the base file already has (named by their token, never by a font name). Nothing else: no spacing, no *Spacing*, no text size, no motion, no font file and no rule, selector or CSS text. The list of tokens an own theme may set, with their kinds and bounds, is written by `cargo xtask gen theme` from the base file into Rust (`crates/bb-core/src/theme/`), so the server, the import and the editor read one list. THM-03 says so.
- **It starts from one built-in theme and stores only what it changes** (M8-Q11). An own theme names the built-in theme it extends (*Daylight*, *Paper*, *Dusk* or *Midnight*) and takes its kind (light or dark) from it; it stores only the values it changes. The values it does not change are read from the built-in theme when its style sheet is made, so a later fix of a built-in theme (M7-F241) reaches it.
- **How it reaches the page** (M8-Q8). The server makes one style sheet for each own theme from its stored values, with one writer in Rust, and serves it at `/themes/{id}.css` under the content security policy `style-src 'self'`, which stays as it is (decision 5). The page links it with a `link` element when the person's choice is an own theme; the address carries the theme's version (`?v=`), so the browser keeps it as long as a hashed asset and a changed theme has a new address. The sheet sets the theme's variables under a frame attribute of its own (`own` in the `frame` line, written to the page as `data-own-theme`), on top of the built-in theme it extends, with its `more=` colours in a block for more contrast. A theme for everyone is served to every signed-in person of the organization, a personal theme only to its maker; any other request gets the answer of a theme that does not exist.
- **Contrast in one place** (M8-Q9). The contrast maths (relative brightness, the ratio, CIE 1976 delta E) and the reading of the `contrast` and `distinct` rules move from the check in `xtask` into `bb-core` (`crates/bb-core/src/contrast/`, pure). `gen theme` writes the rules of the base file into Rust data beside it (DOC-GENERATED). STY-CONTRAST calls it for the built-in files, the server calls it when an own theme is saved or uploaded, and the theme editor calls it through the existing browser module `bb-wasm`, whose size PERF-BUNDLE holds. Each pair gets one rating: *Easy* when it passes the rule for more contrast (7:1 for text), *OK* when it passes its rule, *Hard to read* when it does not. A pair with no stricter rule is rated only *OK* or *Hard to read*: lines (whose minimum for more contrast is their usual minimum), the `distinct` pairs judged by delta E, and the category colors.
- **The draft of the editor.** The unsaved values of the theme editor are kept on the server as the theme's draft and served by the same writer at `/themes/{id}/draft.css?v=<n>`, to its editor only; any other request gets the answer of a theme that does not exist. A new theme cannot be chosen until its first save; until then it is listed to its maker, and a theme for everyone also to the holders of *Change organization settings*, who may finish or delete it (marked `saved: false`). *Save* makes the draft the theme, so the preview needs no style made in the page. The sheet of a draft sets its variables only on the preview of the editor, an element that carries a sample of the built-in theme (`preview` in the `frame` line) and names the draft (`draft`, written as `data-own-draft`), never on the page; it writes the corners and the text faces even where the draft keeps those of the base, so a saved theme the page wears does not show through. The sheet of a saved theme also reaches a sample that names it (`data-own-theme` beside `data-preview-look`), in a block of its own that writes the corners and the faces as the draft's does, so a theme picker shows an own theme in its own colors and shapes and nothing of the page around it.
- **Saving.** A theme for everyone cannot be saved while one of its pairs is *Hard to read*; the refusal names the pairs. A personal theme can be saved with a warning that names them (UX §5.6). An upload (JSON) is checked like a save: an unknown token or a value that its kind does not allow is refused with its name. Themes for everyone are made and changed by holders of *Change organization settings* (*Organization settings › Look › Themes*); any signed-in person makes personal themes (*My settings › Appearance*). The editor takes an edit lock on the theme (ADR-0019).
- **The choices of a theme.** The settings *Light theme* and *Dark theme* list the built-in themes from the generated list (decision 6), then the organization's themes for everyone and the person's own personal themes of that kind. A choice that names an own theme which no longer exists, or which the person may no longer use, counts as the built-in theme it extended.
- **Checks.** STY-CONTRAST grows from the built-in files to every own theme that is saved, with the same code. THEME-ONLY stays: the server's sheet is the only style that is not built from the theme files, and it holds variables only.
- **How it is built (WP-05).** The routes are `/api/v1/themes` (list, make, read, save, take away, `copy`, `file` for a download, `upload`) and the two sheets `/themes/{id}.css?v=<version>` and `/themes/{id}/draft.css?v=<n>`, all in the API description, so SEC-MATRIX runs them for every starting role. A sheet whose address names the version it has now is kept `private, max-age=31536000, immutable`; an address with another version, or none, is asked again (`private, no-cache`). A theme is the look of a person in a browser: only a session reaches the routes, never an access key or an agent. The draft of the editor is the editing draft of ADR-0019 (one draft for each person and theme, kept by `PUT /api/v1/drafts` and the heartbeat, deleted by the save), so the draft sheet is made from the asking person's own draft and nobody else's draft can be served. A new theme, a copy and an upload count against the limits from the moment they are made, saved or not. A setting keeps the choice of an own theme as `<built-in>/<id>`: the server reads it and answers either the theme (`own_theme` in the setting's answer) or the built-in theme in its place; the browser parses nothing. The theme editor reads the readability of each pair from `bb-wasm` (`theme_readability`), the same `bb_core::theme::readability` the server rates a save with.

## Consequences

- A change of look is a change in the theme files (the base, or one theme's color file), and the generated sheet shows it in the diff. A rule exists once: the focus ring, the muted text, the field label.
- Writing a component needs no CSS file and no class name. A style that the person's choices (spacing, text size, motion, contrast) cannot reach cannot be written.
- `cargo xtask gen theme` is part of the build of the browser app and of DOC-GENERATED. The generated sheet is committed, so the server's embedded app needs no extra build step.
- Specificity is that of attribute selectors, so the order in the file is the order in the sheet: a rule for a state is written after the rules for the variants it must win over. Enforced by: review (the order is seen in the diff of the file; the screenshots of the showcase show a change of look).
- Rules for forced colors move to tokens (`forced=`) where one system color serves everywhere; a part keeps a `forced { … }` block where its own colors differ (a disabled button, a link).

## Alternatives considered

- **Keep JSON (`design/theme.json`):** no new dependency, but no comments, long, and the variants of a value would not sit on one line. KDL was chosen.
- **The sister project's way, compiling in the browser:** needs a style element or `adoptedStyleSheets` from a string, which `style-src 'self'` forbids. Rejected.
- **Keep CSS Modules next to the token file:** the situation of the audit. Rejected.
- **A hand-written style sheet with the same data attributes:** the values and the rules would again be in two places that no tool joins, and the theme list could not be generated from it.
- **Tailwind CSS and CSS-in-JS at run time:** rejected in ADR-0010 and still.

## Enforced by

THEME-ONLY (no `style=`, no `className`, no CSS file but the generated one), STY-TOKENS (no color written out), STY-PARTS (every part a rule names is a part some component has), LINT-CSS (the compiled rules use token variables only), STY-CONTRAST (every theme and mode), STY-BOLD (bold only for the parts the `bold` list of the file names, UX §7.3; titles and headings in the display face), DOC-GENERATED (the sheet, the names and the theme choices are the output of the file).
