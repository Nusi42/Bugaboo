# ADR-0005: Search language: one Rust crate, also in the browser

Status: **Accepted** · 2026-10-04

## Context

People need simple filter buttons and an advanced typed search, converting exactly into each other, with the same behavior in the browser and on the server, and without copying another vendor's language.

## Decision

Write **`bb-searchlang`**: lexer, parser, syntax tree, canonical printer, checker and suggestions, with no I/O. Simple search edits the syntax tree; Advanced search edits text that parses into the same tree. Compile the crate to **WebAssembly** (`bb-wasm`) for instant highlighting, suggestions and error messages in the browser. The server compiles the tree to SQL in `bb-store`.

## Consequences

- One grammar (SSOT). Property test: `parse(print(tree)) == tree`.
- WebAssembly adds download size; it's loaded only when search is first used, within its own WebAssembly budget in `tools/checks/perf-bundle.toml` (amendment M5, decision 7).

## Alternatives considered

- **A grammar written twice (Rust and TypeScript):** drifts. Rejected.
- **Parser generators (pest, lalrpop):** fine, but hand-written recursive descent gives better plain-language error messages. Decision left to the milestone, as long as the crate stays I/O-free.

## Amendment M5: the words, the limits and what crosses the wire

The M5 proposals (M5-Q7, Q10) were accepted. Decided:

1. **The parser is written by hand** (recursive descent), for plain-language messages and a small WebAssembly module. No parser generator.
2. **English words** for the language (`and`, `or`, `not`, `is`, `is not`, `contains`, `in last`, `sort by` …). A field is written as on screen, as one word in lower camel case (`assignedTo`, `statusGroup`) *(amended by decision 11: since D3 a field is written as the glossary names it, in lower case with spaces, `assigned to`; the one-word form is still read)*. The word of each built-in field is defined once, next to the field; an own field gets its word from its name by one rule, and a name that cannot be written as one word is written in quotes. The search text is the same in every language of the app, so a shared search works for everyone.
3. **The language holds filters and the order** (`sort by`). How a search is shown (columns, widths, spacing, grouping) is not part of it; a saved search stores that beside the text *(amended by ADR-0034, amendment "Spacing is the person's own": the spacing is the person's setting, and a saved search keeps no spacing)*.
4. **The canonical text is what travels:** the address, the API and a saved search carry the text the printer writes; the tree never crosses the wire. The server parses and checks every search again and never relies on the browser's check.
5. **The checker is given the fields the person may read** (the *readable fields*). A field outside that set is unknown: the same message, the same error code and no difference in time to a field that does not exist (QRY-05).
6. **Limits of the language** (the parser and the checker enforce them): at most 50 filters (a list `in (a, b)` counts as many as it has values), `within N steps` at most 5 (M5-Q10), at most 5 keys in `sort by`, and a text of at most 4 096 bytes (a fix of the review of M5 WP-02: no work is done for a longer text). The time, page and rate limits are the server's (SEC-17, M5 WP-04).
7. **A module of its own** (the lead): the search language is a WebAssembly module of its own, fetched when a search bar first opens, with its own budget in `tools/checks/perf-bundle.toml` (set by M5 WP-02 from its measurement, at most 100 KB with Brotli). The shared budget of 150 KB was planned for Markdown and the search language; the wording of changes and notifications (M4 WP-13) took it, the module is at 145.6 KB, and a list should not fetch Markdown, nor an editor the search language. Each module keeps a budget of its own.
8. **How the module is made** (M5 WP-02): the bindings are a crate of their own, `bb-wasm-search`, loaded by the package `@bugaboo/wasm-search`; `bb-wasm` keeps Markdown and the wording. The browser gives the tree and the readable fields as JSON, which the module reads with a reader that is **generated from the Rust types** (`cargo xtask gen search-reader`, held to the types by DOC-GENERATED): deriving `Deserialize` made the module bigger than its budget (116 KB with Brotli against 100 KB at most), and a reader written by hand would be a second definition of the tree. A tree that is read is held to the rules of a tree (a day of the calendar, an Issue ID by the rules of `bb-core`, a number in its shortest form, `and` and `or` of at least two items with none of their own kind inside; how deep a tree may be is the parser's rule (`MAX_DEPTH`), and a tree that is too deep has no text that reads back), and `print` of the module writes the canonical text of the tree it is given: whether that text reads back as the same tree is held by the tests (TEST-SEARCH-ROUNDTRIP) and, for every text that is saved or run, by the server (`canonical_text` and the check of the text it receives), not by the module. The reader is behind the feature `browser` of `bb-searchlang`, which only `bb-wasm-search` turns on: the server never reads a tree from outside. `bb-searchlang` depends on `bb-core` for the rules of an Issue ID and of a short name, so the browser and the server read an ID the same way (architecture §4, rule 1). Places in the answers are bytes of the UTF-8 text; the package turns them into places in the string. The check that a printed text reads back as the same tree (`canonical_text`) is the feature `round-trip-guard` of `bb-searchlang`: the server and the tests build with it, so a defect of the printer can never be saved or run, and the module of the browser builds without it, because the check costs about 7 KB of the module (its budget in `perf-bundle.toml`); everything the browser prints is sent to the server, which parses and checks it again, and no path of the browser depends on the check to refuse a text. Measured at 88.9 KB with Brotli at the server's quality; the budget line is in `tools/checks/perf-bundle.toml`.

Enforced by: TEST-SEARCH-ROUNDTRIP (decisions 1 to 4, the printer and the parser), the tests of M5 WP-02 (decisions 5 and 6), SEC-MATRIX with the `search` entry point (decision 5 on the server), PERF-BUNDLE (decision 7).

9. **Values are written as the person sees them** (the lead, from the review of M5 WP-04): a status, an issue type and a choice of an own field are written by their name as shown on screen (`status is "In progress"`, `type is Bug`), never by a stored key or ID; two names are the same by the one rule that keeps names apart everywhere in the app (`bb_core::names::same_name`: case and repeated spaces do not count, accents do), so the checker, the choice lists and the server compare alike. The choices of built-in fields (*Priority*, *Status group*) are words of the language like the field words: one English word each, defined once next to the choice and the same in every language of the app, never the text of the message catalog. The server turns a name into the things of that name that the person may see, at the moment the search runs; a name the person cannot see is an unknown value, with the same message as a name that does not exist. A rename makes the old name unknown in a saved search, and the checker says so; nothing silently matches something else. A person or a group may be named in a search when the person searching may see that name by *Who sees people* (ADR-0022, the people kind of the field); `member of "…"` also needs being in the group or *Manage groups*, because its results show who is in the group. A project is named by its current short name and an issue by its Issue ID (`bb-core`), and both only when the person sees them. One function resolves every name of a search, for running it and for checking a saved search (the lead, from the reviews of M5 WP-04 and WP-06). Each word of the language (built-in fields, the words of *yes* and *no*, the operators each kind of field allows) is defined once, next to the field, and a word belongs to one field for everyone: an own field never takes the word of a built-in field, also not of one the person may not read or that cannot be searched yet.

10. **Lengths of time are written in hours and minutes** (the lead, M5-F41): a field of lengths of time takes `2 hours`, `45 minutes` or `1 hour 30 minutes`, never a number of seconds. The units have one fixed length, `minute`/`minutes` and `hour`/`hours` only: days and weeks would depend on working hours, and a search text means the same for everyone and in every organization. The printer writes the canonical form in words (`1 hour 30 minutes`, `90 minutes` is `1 hour 30 minutes`). A bare number for such a field is a mistake with a plain message that shows how to write it (`search.mistake.wrong-duration`); a length of time for a field of numbers is a mistake too. The tree holds whole minutes (`Operand::Duration`) and the server turns them into the seconds the field stores. The search bar writes the same words on the filter button and in its window. A length of time is never a choice: `size is 2 hours` is a mistake for a field with a list of choices, even when a choice is spelled like it. One function (`Operand::spelling`) writes the words of a value for the checker, the printer and the store, and `TimeUnit` carries the minutes of each unit. The words `minute(s)` and `hour(s)` are keywords from this decision on: an own field with one of these words is written in quotes by the printer (`"hours" is 3`), a text that wrote it bare before is still read by the field of that word and printed with quotes (canonical print, M5 WP-07). Repeated or reversed units (`30 minutes 1 hour`) are accepted and printed in the canonical order. Enforced by: the vectors of the language (`cargo xtask gen search-vectors`, with `timeSpent`), TEST-SEARCH-ROUNDTRIP.

11. **The words of the glossary, with spaces and in display case** (decision D3 of the exit polish of M5): a field is written as the glossary names it, in lower case and with spaces (`status group`, `assigned to`, `found in release`), and the values of the built-in lists in display case (`priority is High`, `status group is not Done`; a value of several words is quoted, as every name with spaces is: `"In progress"`). The name of a field runs up to the word that starts what is asked of it (`is`, `in last`, `contains`, `member of`, `within`) or joins or orders (`and`, `or`, `not`, `sort`, a direction); a name that would be cut by one of these words is written in quotes. As a key of `sort by`, a name that begins with the words of a direction (`highest`, `z to`) is written in quotes too, because after a key those words are its direction (`sort by status, "z to"`); the parser, the end of a name and the printer share the one rule of where a direction begins (`words::starts_direction`, found by TEST-SEARCH-ROUNDTRIP). One rule tells two words apart (`bb_core::fields::word_key`: lower case, no space), so the form of the old language (`statusGroup`, `assignedTo`, `inProgress`, any case) still reads, and a saved search stored in it loads. **After a text is read with the fields it is for, every field and every value of a fixed list is put in the words the field gives** (`bb_searchlang::parse_with`), so the canonical text, the address, a saved search and the filter buttons show the new words and the round trip between Simple and Advanced search stays lossless (TEST-SEARCH-ROUNDTRIP). The word of a built-in field is its key with spaces, of an own field its name as names are told apart (`names::name_key`); the choices of *Priority* and *Status group* are `code_phrase` of their codes. Hidden fields do not change: only the readable fields are looked at, for the match, the mistake and the suggestions, so no glossary name of a hidden field is given away (QRY-05). Where a text stops before its end (`prio is High and `), the mistakes of what stands before the place come first, in reading order. The words of columns and grouping kept in an address or a saved presentation are read by the same rule for the built-in fields. Enforced by: TEST-SEARCH-ROUNDTRIP, the tests `qry_05_…` of `bb-searchlang`.
