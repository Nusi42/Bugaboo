# Testing, sample data and local ports

## Test layers

| Layer | Tool | What it covers | Runs |
|-------|------|----------------|------|
| Unit | `cargo test`, Vitest (Vite-based) | Pure logic: search language, Markdown, policy evaluation, working-time rules, UI helpers | every push |
| Property | proptest | Search round trip, ID generation, permission invariants | every push |
| Use case | `cargo test` with in-memory fakes | Every `bb-app` use case: permissions, events, validation | every push |
| Repository | `cargo test` against **SQLite and PostgreSQL** | SQL, migrations, search compiler | CI |
| API | Rust integration tests against a running server | Endpoints, OpenAPI conformance, security headers, permission matrix | CI |
| End to end | **Playwright** driving the real app (built with **Vite**) | Key journeys on desktop and phone sizes, all four themes, accessibility (axe) | CI |
| Concurrency | Playwright (10 people) + `cargo xtask load` | Edit locks, conflicts, simultaneous changes, no lost text | CI (short), nightly (long) |
| Performance | `cargo xtask dataset large` + benchmarks | PERF budgets on 1 M issues | nightly |

## Sample organization

A realistic, **fully fictional** organization used for development, end-to-end tests, demos and the optional "try it out" mode (OPS-12). Generated by `cargo xtask dataset sample`, deterministic from a seed (default 42), in under a minute, into SQLite or PostgreSQL.

### People (50) and groups

- 2 Administrators, 4 Project leads, 30 Team members, 8 Contributors, 4 Viewers, 2 Guests, plus 1 bot account.
- Groups: Backend, Frontend, Mobile, QA, Support, Docs, Management, External.
- Generated names from a mixed international name list; e-mail addresses under the reserved domain `bugaboo.example`, so nothing can ever reach a real inbox.
- Each person has a time zone, some have passkeys, two-step sign-in or access keys. Two people are already **removed** (*Former user* labels) to test GDPR flows.

### Projects (4, two with sub-projects) — about 10,000 issues

| Project | Short name | IDs | Sub-projects | Issues |
|---------|------------|-----|--------------|--------|
| Mobile app | APP | random | iOS (`IOS`), Android (`AND`) | ≈ 4,800 |
| Website | WEB | counting | Shop (`SHOP`), Blog (`BLOG`) | ≈ 3,000 |
| Operations | OPS | random | — | ≈ 1,800, including restricted security issues |
| Handbook | DOC | counting | — | ≈ 400, mostly documents and tasks |

### What's inside

- **Issues** over the last 18 months (dates are shifted at generation time, so the data always looks current): Bug 45 %, Task 30 %, Feature 20 %, Goal 5 %; realistic status ages, priorities and labels; own fields (Severity, Platforms, Customer); about 2 % restricted issues.
- **Sub-issues** under goals, and about 3,000 **relations** of every kind, including chains deeper than four steps and one deliberate *blocks* circle (to test the warning).
- **Releases:** three per project, one in the past, one current, one planned.
- **Comments:** about 30,000, with mentions; some edited.
- **Files and documents:** about 500 small generated attachments (images, PDFs), 60 pages and 20 files with several versions each.
- **Time:** about 20,000 time entries with activities and cost centers, six months of working hours for every employee (including some broken working-time rules), and a few running timers.
- **Configuration:** workflows for each issue type, field permissions (for example *Cost center* hidden from Contributors), *Who sees people* set for Guests, fields excluded from AI, saved searches, dashboards, two custom themes.
- **States worth testing:** an edit lock held by someone, a pending conflict, a closed month, a person with a removal in progress.

### Large dataset

`cargo xtask dataset large --issues 1000000` builds the same shape at the PERF scale (500 people, 500 projects) for benchmarks.

## Ten people at the same time

Concurrency is tested with **10 simulated people** from the sample organization, each in their own browser context (Playwright) or API client (`cargo xtask load --people 10`):

| Scenario | What must hold |
|----------|----------------|
| Three people try to edit the same description | One gets the lock; the others see *"… is editing"*; *Edit anyway* moves the lock and keeps the first person's draft |
| Two people change the status of the same issue within a second | One wins; the other sees the conflict message; nothing is half-saved |
| A lock holder's network drops | The lock frees itself within a minute; their text is kept as a draft and offered with *Compare and save* |
| Everyone drags cards on the same board | Final board matches the event log; every person's screen shows the final state after refresh |
| Timers and working hours start and stop at the same time | No double entries; working-time rules evaluated once per change |
| Searches while others change data | Results respect permissions at every moment; no errors; latency within budget |

Enforced by: TEST-CONCURRENT, TEST-EDIT-LOCKS.

Each scenario runs against **both SQLite and PostgreSQL**. The short version (2 minutes) runs in CI; the long version (30 minutes, mixed workload) runs nightly and checks invariants afterwards: every change has an event, no lock outlives its lease, no text is lost.

## Local ports (ADR-0023)

Your machine runs other Vite projects, so Bugaboo never uses default ports. All ports live in **`tools/dev/ports.json`** (single source); Vite, Playwright, the server and xtask read them from there, and every tool uses `strictPort`, so a busy port fails with a clear message instead of silently moving.

| Port | Used by |
|------|---------|
| 47200 | Bugaboo server in development (API + embedded app) |
| 47201 | Vite dev server (hot reload) |
| 47202 | Vite preview of a production build |
| 47203 | Server instance for end-to-end tests (fresh sample database) |
| 47204 | Vitest UI |
| 47210–47229 | Parallel Playwright workers, one server and database each |
| 47230 | Load-test server |

The installed product asks for its port in the setup wizard (suggesting 8443 and checking that it's free); these development ports never appear in a customer installation.
