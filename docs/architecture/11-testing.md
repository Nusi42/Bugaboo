# Testing, sample data and local ports

## Test layers

| Layer | Tool | What it covers | Runs |
|-------|------|----------------|------|
| Unit | `cargo test`, Vitest (Vite-based) | Pure logic: search language, Markdown, policy evaluation, working-time rules, UI helpers | every push |
| Property | proptest | Search round trip, ID generation, permission invariants | every push |
| Use case | `cargo test` with in-memory fakes | Every `bb-app` use case: permissions, events, validation | every push |
| Repository | `cargo test` against **SQLite and PostgreSQL** | SQL, migrations, search compiler | CI |
| API | Rust integration tests against a running server | Endpoints, OpenAPI conformance, security headers, permission matrix | CI |
| End to end | **Playwright** driving the real app (built with **Vite**) | Key journeys on desktop and phone sizes, all four themes, accessibility (axe) | CI |
| Concurrency | Playwright (10 people) + `cargo xtask load` | Edit locks, conflicts, simultaneous changes, no lost text | CI (short), nightly (long) |
| Performance | `cargo xtask dataset large` + benchmarks | PERF budgets on 1 M issues | nightly |

## Database tests

Every repository test runs against **SQLite and PostgreSQL** (ADR-0003). Nothing is installed machine-wide (ADR-0024).

- **PostgreSQL 18.6** is a pinned tool in `tools/dev/tools.toml`. On Windows `cargo xtask setup` downloads the official binaries (checksum checked) into `.tools/postgresql/`. On Linux it uses the system PostgreSQL (on the `PATH`, or under `/usr/lib/postgresql/*/bin` as on GitHub's Ubuntu runners) and explains how to install it when missing.
- **`cargo xtask db start | stop | reset | url`** manages a throwaway cluster in `.tools/pg-data/`. It listens on `127.0.0.1` only, on the port `postgres` from `tools/dev/ports.json` (strict: a busy port is an error). Its random password lives in `.tools/pg-password`, never in the repository; on Windows the file is protected only by the inherited permissions of your user profile, on Unix it is readable by its owner only. All work folders share port 47240 (ADR-0023), so only one `cargo xtask ci` or `db start` runs at a time on a machine. `db url` prints the connection URL for tools of your own.
- **`cargo xtask db run -- <command>`** starts the cluster if needed, runs the command with `BB_TEST_DATABASES=sqlite,postgres`, `BB_TEST_POSTGRES_URL` and `BB_DB_PARITY_FILE` set, stops the cluster again if it started it (also after an error), and then checks the parity record against ARCH-DB-PARITY and DATA-MIGRATIONS. Before the run it deletes the old record and any `bbtest_*` databases left behind by killed test programs; after a failure it deletes the record again, so an old or partial record never decides anything. `cargo xtask ci` runs the Rust tests this way.
- **Writing a test:** `bb_testing::each_database("name", async |db| { … }).await` runs the body once per selected database. The body gets a typed pool (`db.pool()` is `Pool::Sqlite` or `Pool::Postgres`; `tests/example_repository.rs` in `bb-testing` shows the pattern). Each run gets an empty database of its own (a temporary file for SQLite, a freshly created and afterwards dropped database for PostgreSQL), so tests never see each other's data. Without `BB_TEST_DATABASES`, plain `cargo test` runs SQLite only.
- **The record** `target/db-parity.txt` has one line per finished run (`<database> <test name>`). ARCH-DB-PARITY fails when a test ran on one database but not the other, or when a database did not run at all. DATA-MIGRATIONS additionally forbids `.sql` migration files and, once `bb-store` has migrations, wants its `migrations` test in the record for both databases. Both rules on the record run only inside `cargo xtask db run`, right after the tests; `check all` never reads a record left on disk (it can be from an older state of the code). There, ARCH-DB-PARITY checks that `cargo xtask ci` runs the Rust tests through `db run`, and DATA-MIGRATIONS checks for `.sql` files.

Enforced by: ARCH-DB-PARITY, DATA-MIGRATIONS.

## Sample organization

A realistic, **fully fictional** organization used for development, end-to-end tests, demos and the optional "try it out" mode (OPS-12). Generated by `cargo xtask dataset sample`, deterministic from a seed (default 42), in under a minute, into SQLite or PostgreSQL.

### Making it and using it

`cargo xtask dataset sample [--seed N] [--database sqlite|postgres] [--out <folder>] [--check]` runs the `bb-sample` program (crate `bb-sample`, [architecture §4](04-building-blocks.md#bb-sample)) as a process, so `xtask` depends on no product crate. The program makes the organization through the same use cases the API calls: the first administrator with the setup code, everybody else as that administrator by invitation, so every change has its event and its security log entry and nothing is written to the database by hand. It is deterministic from the seed (default 42) with its own random source; it never reads the clock, because every date comes from one start moment that `xtask` passes in (now; a fixed moment for `--check`). On SQLite it takes a few seconds.

- **Names:** the folders the sample is made in, the names of its files and the environment variable of the PostgreSQL address are written once, in `tools/dev/sample.json`; `xtask`, the `bb-sample` program and the end-to-end tests all read that file.
- **What it makes in `<out>`** (default `target/sample`, `target/sample-postgres` on PostgreSQL): `data/` is a data folder that `bugaboo serve --data-dir` can start on (copy it first); `sign-in.txt` has one line per person (e-mail address, random password, role, name, the secret of the code app for the few people who have one, and the access key for the three who have one; the columns are separated by tabs, an empty column stays empty); `dump.json` is the canonical dump; `sample.json` marks the folder as made by the tool, so the next run may empty it and a folder with anything else in it is left alone. The passwords are random for every run and come from the operating system, never from the seed: no password is in the repository, and `sign-in.txt` is the only file that holds one (in `target/`, which Git ignores).
- **On PostgreSQL** the program uses an empty database in the throwaway cluster of `cargo xtask db` (started and stopped by the command when needed). The address goes to the program in the environment variable `BB_SAMPLE_DATABASE_URL`, never on its command line.
- **People and organization:** 50 fictional people with the mix of roles below, recorded in the plan (`roster`) and in the dump. After the people, `bb_sample::Organization` (the one filling of the extension point `bb_sample::Later`) makes the groups, the custom roles, the projects with their sub-projects and every row of *Who has which role*, as the first administrator, through the use cases of M2 (a change every second of the sample's clock, so the records come in the same order every time). Each person also chose a time zone and how dates and numbers are written, as they do in *My settings*, and a few have an access key. Names come from `crates/bb-sample/data/names.toml`, written for Bugaboo (no third-party name data); every address is under `bugaboo.example`. The people the demos name are the same whatever the seed: Ada Brandt (the administrator who runs the demo), Ana Moreno (a Contributor, on *Website* through the group *External* and nowhere else) and Ben Hale (a Team member for the whole organization, with *No access* on *Android*). The names of the groups, projects and custom roles are written once, in `tools/dev/sample.json`, which the program, `xtask` and the end-to-end tests read.
- **Using it in browser tests:** `cargo xtask dev --sample` makes a fresh sample and starts the server on it (it prints where `sign-in.txt` is). A file of end-to-end tests that says `test.use({ sample: true })` gets a server on a fresh copy of `target/sample/data` (one server per Playwright worker, ADR-0023 ports) and reads the people from `samplePeople()` (`web/app/e2e/support/sample.ts`). `cargo xtask ci` makes the sample before the browser tests; by hand, run `cargo xtask dataset sample` first. The M1 tests of setup and signing in still start from an empty data folder.
- **The check:** `cargo xtask dataset sample --check` makes the organization twice on SQLite and twice on PostgreSQL from one seed into `target/sample-check/` and compares the canonical dumps. The dump leaves out what is random by design (IDs, password hashes, secrets and the hashes of the security log) and replaces each ID by a label that counts the records of a kind in the order they appear (`person#3`), so it still says which events and entries are about the same record. The run fails when two dumps differ, when an address is not under `bugaboo.example`, when a name is not a given name and a family name of the list, or when a password, secret or access key of `sign-in.txt` is found in any other file of a run (the database, the keys, the log files, the dump, what the program said). The dump also holds the groups with their members, the roles with how many people hold each, the projects with their leads, every row of *Who has which role* and the levels projects and custom roles set; the run fails when a group or project of this section is missing, when a role of the mix below is missing or held by another number of people, or when a project has no Project lead. The rules and their failing and passing examples are in `xtask/src/checks/test_sample_data.rs` and `tools/checks/fixtures/TEST-SAMPLE-DATA/`.

Enforced by: TEST-SAMPLE-DATA (`cargo xtask ci` runs it), ARCH-HTTP-EDGE (`bb-sample` is the second crate that may wire an adapter), SEC-SECRETS (no password in the repository).

### The M2 exit demo on the sample

`web/app/e2e/m2-exit-demo.spec.ts` runs it in `cargo xtask ci`, on a phone and a computer, with axe in the four themes at every step; with `BB_SCREENSHOT_DIR` set the same run takes the pictures of the review page (`M2/demo/<step>-<phone|computer>-<light|dark>.png`). By hand, with `cargo xtask dev --sample` (it prints where `sign-in.txt` is; sign in as Ada Brandt, the first line):

1. *Organization settings › Roles & permissions*: make the role *Reviewer* from a copy of *Viewer* and tick *See how the server is doing*.
2. *Website › Project settings › Field permissions*: for *Contributor* set *Cost center* to *Hidden*. *Mobile app* has it hidden already; *Shop* and *Blog* show it hidden "from Website".
3. *Website › Project settings › Who sees people*: for *Guest* set *Assigned to* to *Hidden*; the preview now says *Someone*.
4. *Website › Project settings › Check access*: pick Ana Moreno and read why she is a Contributor (through the group *External*) and that *Cost center* is hidden from her. Pick Ben Hale in *Android* to read that *No access* wins over his role.
5. Sign out; sign in as the Guest of *Website* (see `dump.json`, the row with the role *Guest* on `WEB`) and as Ana: the tree shows *Website* with its sub-projects only, and the settings pages and *Mobile app* are not found.

## Ten people at the same time

Concurrency is tested with **10 simulated people** from the sample organization, each in their own browser context (Playwright) or API client (`cargo xtask load --people 10`):

| Scenario | What must hold |
|----------|----------------|
| Three people try to edit the same description | One gets the lock; the others see *"… is editing"*; *Edit anyway* moves the lock and keeps the first person's draft |
| Two people change the status of the same issue within a second | One wins; the other sees the conflict message; nothing is half-saved |
| A lock holder's network drops | The lock frees itself within a minute; their text is kept as a draft and offered with *Compare and save* |
| Everyone drags cards on the same board | Final board matches the event log; every person's screen shows the final state after refresh |
| Timers and working hours start and stop at the same time | No double entries; working-time rules evaluated once per change |
| Searches while others change data | Results respect permissions at every moment; no errors; latency within budget |

Enforced by: TEST-CONCURRENT, TEST-EDIT-LOCKS.

Each scenario runs against **both SQLite and PostgreSQL**. The short version (2 minutes) runs in CI; the long version (30 minutes, mixed workload) runs nightly and checks invariants afterwards: every change has an event, no lock outlives its lease, no text is lost.

## Local ports (ADR-0023)

Your machine runs other Vite projects, so Bugaboo never uses default ports. All ports live in **`tools/dev/ports.json`** (single source); Vite, Playwright, the server and xtask read them from there, and every tool uses `strictPort`, so a busy port fails with a clear message instead of silently moving.

| Offset | Used by |
|--------|---------|
| 0 | Bugaboo server in development (API + embedded app) |
| 1 | Vite dev server (hot reload) |
| 2 | Vite preview of a production build |
| 3 | Server instance for end-to-end tests (fresh sample database) |
| 4 | Vitest UI |
| 10–29 | Parallel Playwright workers, one server and database each |
| 30 | Load-test server |
| 40 | Throwaway PostgreSQL for tests (`cargo xtask db start`) |

The offsets are inside a block of 100 ports. Each work folder `bugaboo.winN` has its own block, starting at 47200 + (N − 1) · 100 (`win1` 47200–47299, `win3` 47400–47499, up to `win9` 48000–48099), so folders that build and test at the same time never share a port; any other folder uses block 1 and `BUGABOO_PORT_BLOCK` names another one. The table above shows block 1: the server of the first folder is on 47200, of the third on 47400.

The installed product asks for its port in the setup wizard (suggesting 8443 and checking that it's free); these development ports never appear in a customer installation.
