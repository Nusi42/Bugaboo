# Testing, sample data and local ports

## Test layers

| Layer | Tool | What it covers | Runs |
|-------|------|----------------|------|
| Unit | `cargo test`, Vitest (Vite-based) | Pure logic: search language, Markdown, policy evaluation, working-time rules, UI helpers | every push |
| Property | proptest | Search round trip, ID generation, permission invariants | every push |
| Use case | `cargo test` with in-memory fakes | Every `bb-app` use case: permissions, events, validation | every push |
| Repository | `cargo test` against **SQLite and PostgreSQL** | SQL, migrations, search compiler | CI |
| API | Rust integration tests against a running server | Endpoints, OpenAPI conformance, security headers, permission matrix | CI |
| End to end | **Playwright** driving the real app (built with **Vite**) | Key journeys on desktop and phone sizes, all four themes, accessibility (axe); the issue page, the new-issue dialog and the edit locks also on a phone in **WebKit** | CI |
| Concurrency | Playwright (10 people) + `cargo xtask load` | Edit locks, conflicts, simultaneous changes, no lost text | CI (short), nightly (long) |
| Performance | `perf-issues.spec.ts` on the sample (project `speed`); `cargo xtask dataset large` + benchmarks | PERF-01 on the 10,000 issues of the sample (CI), PERF budgets on 1 M issues (nightly) | CI, nightly |

## Database tests

Every repository test runs against **SQLite and PostgreSQL** (ADR-0003). Nothing is installed machine-wide (ADR-0024).

- **PostgreSQL 18.6** is a pinned tool in `tools/dev/tools.toml`. On Windows `cargo xtask setup` downloads the official binaries (checksum checked) into `.tools/postgresql/`. On Linux it uses the system PostgreSQL (on the `PATH`, or under `/usr/lib/postgresql/*/bin` as on GitHub's Ubuntu runners) and explains how to install it when missing.
- **`cargo xtask db start | stop | reset | url`** manages a throwaway cluster in `.tools/pg-data/`. It listens on `127.0.0.1` only, on the port `postgres` from `tools/dev/ports.json` (strict: a busy port is an error). Its random password lives in `.tools/pg-password`, never in the repository; on Windows the file is protected only by the inherited permissions of your user profile, on Unix it is readable by its owner only. All work folders share port 47240 (ADR-0023), so only one `cargo xtask ci` or `db start` runs at a time on a machine. `db url` prints the connection URL for tools of your own.
- **`cargo xtask db run -- <command>`** starts the cluster if needed, runs the command with `BB_TEST_DATABASES=sqlite,postgres`, `BB_TEST_POSTGRES_URL` and `BB_DB_PARITY_FILE` set, stops the cluster again if it started it (also after an error), and then checks the parity record against ARCH-DB-PARITY and DATA-MIGRATIONS. Before the run it deletes the old record and any `bbtest_*` databases left behind by killed test programs; after a failure it deletes the record again, so an old or partial record never decides anything. `cargo xtask ci` runs the Rust tests this way.
- **Writing a test:** `bb_testing::each_database("name", async |db| { … }).await` runs the body once per selected database. The body gets a typed pool (`db.pool()` is `Pool::Sqlite` or `Pool::Postgres`; `tests/example_repository.rs` in `bb-testing` shows the pattern). Each run gets an empty database of its own (a temporary file for SQLite, a freshly created and afterwards dropped database for PostgreSQL), so tests never see each other's data. Without `BB_TEST_DATABASES`, plain `cargo test` runs SQLite only.
- **The record** `target/db-parity.txt` has one line per finished run (`<database> <test name>`). ARCH-DB-PARITY fails when a test ran on one database but not the other, or when a database did not run at all. DATA-MIGRATIONS additionally forbids `.sql` migration files and, once `bb-store` has migrations, wants its `migrations` test in the record for both databases. Both rules on the record run only inside `cargo xtask db run`, right after the tests; `check all` never reads a record left on disk (it can be from an older state of the code). There, ARCH-DB-PARITY checks that `cargo xtask ci` runs the Rust tests through `db run`, and DATA-MIGRATIONS checks for `.sql` files.

Enforced by: ARCH-DB-PARITY, DATA-MIGRATIONS.

## Sample organization

A realistic, **fully fictional** organization used for development, end-to-end tests, demos and the optional "try it out" mode (OPS-12). Generated by `cargo xtask dataset sample`, deterministic from a seed (default 42), into SQLite or PostgreSQL. The people and the organization take a few seconds; the 10,000 issues with their comments take about six minutes (see *Issues of the sample* below), which is why `--check` and `cargo xtask dev --sample` make a smaller one.

### Making it and using it

`cargo xtask dataset sample [--seed N] [--database sqlite|postgres] [--issues N] [--out <folder>] [--check]` runs the `bb-sample` program (crate `bb-sample`, [architecture §4](04-building-blocks.md#bb-sample)) as a process, so `xtask` does not link the store or the use cases. The program makes the organization through the same use cases the API calls: the first administrator with the setup code, everybody else as that administrator by invitation, so every change has its event and its security log entry and nothing is written to the database by hand. It is deterministic from the seed (default 42) with its own random source; it never reads the clock, because every date comes from one start moment that `xtask` passes in (now; a fixed moment for `--check`). The people and the organization take a few seconds on SQLite; the issues take minutes (see *Issues of the sample*).

- **Names:** the folders the sample is made in, the names of its files and the environment variable of the PostgreSQL address are written once, in `tools/dev/sample.json`; `xtask`, the `bb-sample` program and the end-to-end tests all read that file.
- **What it makes in `<out>`** (default `target/sample`, `target/sample-postgres` on PostgreSQL): `data/` is a data folder that `bugaboo serve --data-dir` can start on (copy it first); `sign-in.txt` has one line per person (e-mail address, random password, role, name, the secret of the code app for the few people who have one, and the access key for the three who have one; the columns are separated by tabs, an empty column stays empty); `dump.json` is the canonical dump; `sample.json` marks the folder as made by the tool, so the next run may empty it and a folder with anything else in it is left alone. The passwords are random for every run and come from the operating system, never from the seed: no password is in the repository, and `sign-in.txt` is the only file that holds one (in `target/`, which Git ignores).
- **On PostgreSQL** the program uses an empty database in the throwaway cluster of `cargo xtask db` (started and stopped by the command when needed). The address goes to the program in the environment variable `BB_SAMPLE_DATABASE_URL`, never on its command line.
- **People and organization:** 50 fictional people with the mix of roles below, recorded in the plan (`sample_people`) and in the dump. After the people, `bb_sample::Organization` (the one filling of the extension point `bb_sample::Later`) makes the groups, the custom roles, the projects with their sub-projects and every row of *Who has which role*, as the first administrator, through the use cases of M2 (a change every second of the sample's clock, so the records come in the same order every time). Each person also chose a time zone and how dates and numbers are written, as they do in *My settings*, and a few have an access key. Names come from `crates/bb-sample/data/names.toml`, written for Bugaboo (no third-party name data); every address is under `bugaboo.example`. The people the demos name are the same whatever the seed: Ada Brandt (the administrator who runs the demo), Ana Moreno (a Contributor, on *Website* through the group *External* and nowhere else) and Ben Hale (a Team member for the whole organization, with *No access* on *Android*). The names of the groups, projects and custom roles are written once, in `tools/dev/sample.json`, which the program, `xtask` and the end-to-end tests read.
- **Issues of the sample (M3 WP-11):** after the organization, `bb_sample::Everything` (the filling of the extension point that `bb-sample` runs) makes the issues of *Projects* below: the starting issue types and kinds of relation, how each project gives out its IDs, the own fields *Severity*, *Platforms* and *Customer*, the groups of labels and the labels, then every issue, sub-issue, tag, label, status change, relation and comment (some edited), and at the end one edit lock held and one draft waiting. All of it goes through the use cases, one change at a time, by the Administrators and Team members of the whole organization, each signed in on the working days they work (Monday to Friday, from nine, the clock of the sample running through eighteen months), so every date is a working day and every issue has a person who made it. The plan (`crates/bb-sample/src/issues_plan.rs`) has no database in it: it is worked out from the seed and the counts of `tools/dev/sample.json` (`issues`: the full count, the small count, the share of each type, of each project and place, the own fields, labels and tags, the numbers of relations and comments), and its words are in `crates/bb-sample/data/issues.toml`. `--issues N` scales every count to N issues (the full sample is `issues.total`, 10,000; `--check` and `cargo xtask dev --sample` make `issues.smallTotal`, 500). The readable IDs of the projects with *Random IDs* are the only thing that differs from run to run, and the dump leaves them out. No issue is restricted, and there are no releases. The history of every issue is read from the events at the end (what the daily job `history.catch-up` does), so the first page that shows one does not have to. The program is built with optimisations for this, as it runs about seventy thousand use cases: the full sample takes about six minutes on SQLite (the people and the organization, three seconds), the small one twenty seconds. Enforced by: TEST-SAMPLE-DATA (the dump of every `--check` run holds the numbers of the plan).
- **Using it in browser tests:** `cargo xtask dev --sample` makes a fresh sample and starts the server on it (it prints where `sign-in.txt` is). A file of end-to-end tests that says `test.use({ sample: true })` gets a server on a fresh copy of `target/sample/data` (one server per Playwright worker, ADR-0023 ports) and reads the people from `samplePeople()` (`web/app/e2e/support/sample.ts`). `cargo xtask ci` makes the sample before the browser tests; by hand, run `cargo xtask dataset sample` first. The M1 tests of setup and signing in still start from an empty data folder.
- **Working together (M4 WP-10):** the same program goes on after the issues, in three parts, all through the use cases. (1) *Before the issues* the project `OPS` gets a workflow of its own, *Operations*, made the way the editor makes it (*Create*, the edit lock, *Publish*): the starting workflow with the status change *Open* to *In progress* asking for *Assigned to* (*Ask for*); every other place keeps the starter workflows *Simple*, *Bug* and *Development* of the first start. The walk of the status changes (`Maker::status`) supplies what a change asks for. (2) *After the issues* `Maker::work_together` (`together.rs`, `together_files.rs`) lets the people who are not on the team do their part (M3-F111): the Viewers follow issues (`viewerFollows`), the Contributors and Guests report issues of their own in the projects where they hold a role and comment under them (`reports`), the Contributors change the title and tags of what they reported (`contributorChanges`; a Contributor cannot change a status, so none is tried), the Team members change statuses under the workflows, many of them on followed issues (`teamStatusChanges`), and about five hundred small files are added to issues and comments (`files`: pictures as PNG or JPEG and one-page PDFs, generated so that no two are the same file, by `bb_files::fixtures::varied_picture` and `varied_pdf`). The files are kept in the `files/` folder of the data folder, and the previews are made by the job runner (`Ctx::run_due_jobs`, with `PreviewCommand::in_process`), so every file has its preview when the sample is done. (3) *At the end* the notifications come from the sample's own changes (the reader of the outbox, run by the same `run_due_jobs`), and the Viewers, Guests and Contributors mark `readPercent` of theirs as read. The counts are those of `issues.work` in `tools/dev/sample.json`, scaled like the issues (`WorkPlan::counts`, the one place both the program and the judge read them). The dump has a part `issues.work`: the workflows (statuses, changes, changes that ask), the projects with a workflow of their own, the files (pictures, PDFs, on comments, previews), the notifications (by kind, by the role of the person, read, and the ones a Guest got about an issue they did not report: none), the reports by role, the status changes of the team, the changes of Contributors and the follows of Viewers. The dump lists the people an issue is assigned to by label, since the order of their random IDs is not part of the organization. Enforced by: TEST-SAMPLE-DATA (`WorkPlan::judge` in `bb-dev-words`, the tests `m3_f111_…`, `att_04_…`, `wf_04_…` of `bb-sample`).
- **The check:** `cargo xtask dataset sample --check` makes the organization twice on SQLite and twice on PostgreSQL from one seed into `target/sample-check/` and compares the canonical dumps. The dump leaves out what is random by design (IDs, password hashes, secrets and the hashes of the security log) and replaces each ID by a label that counts the records of a kind in the order they appear (`person#3`), so it still says which events and entries are about the same record. The run fails when two dumps differ, when an address is not under `bugaboo.example`, when a name is not a given name and a family name of the list, or when a password, secret or access key of `sign-in.txt` is found in any other file of a run (the database, the keys, the log files, the dump, what the program said). The dump also holds a part `issues`: for each project the issues of each type, status and priority, the sub-issues, the relations of each kind with the longest chain of *blocks* and the number of circles, tags, labels, the values of each own field, the comments (and how many were edited) and the locks and drafts left behind, and the run fails when they are not the plan of `tools/dev/sample.json` scaled to the issues asked for, within `issues.tolerancePercent` (`IssuePlan::problems` in `bb-dev-words`, which the tests of `bb-sample` ask as well). The dump also holds the groups with their members, the roles with how many people hold each, the projects with their leads, every row of *Who has which role* and the levels projects and custom roles set; the run fails when a group or project of this section is missing, when a role of the mix below is missing or held by another number of people, or when a project has no Project lead. The rules and their failing and passing examples are in `xtask/src/checks/test_sample_data.rs` and `tools/checks/fixtures/TEST-SAMPLE-DATA/`.

Enforced by: TEST-SAMPLE-DATA (`cargo xtask ci` runs it), ARCH-HTTP-EDGE (`bb-sample` is the second crate that may wire an adapter), SEC-SECRETS (no password in the repository).

### Speed on the sample

`web/app/e2e/perf-issues.spec.ts` (the Playwright project `speed`, which runs after every other project so nothing competes for the computer; by hand `--project=speed --no-deps`) measures the reads of an issue page (the issue, its relations, sub-issues, related issues, history, tags and labels, follow and followers, asked all at once as the browser does) and the first pages of every project's list on the ten thousand issues, then the same with ten people writing comments and one reading, and the preview of a move. PERF-01 is the 95th percentile under 100 ms, with the program the tests run against (`BB_SERVER_BIN` names another build); the numbers go to `test-results/perf-*.json`. On the sample, in a debug build: pages 38 ms, lists 44 ms, a comment with ten writers 64 ms (release: 18, 17 and 39 ms). `perf_05_…` (`bb-server`, both databases) counts the statements a read runs (`Database::statements_run`) and fails when an issue with many comments, relations, sub-issues and tags runs more than one with two, or a page of forty issues more than a page of five. The project `speed` has one retry: on a busy computer run it alone (`--project=speed --no-deps`), because a speed test that other work competes with measures the other work. Enforced by: TEST-SAMPLE-DATA (the sample the speed is measured on).

## Ten people at the same time

Concurrency is tested with **10 simulated people** (an administrator and Team members of one project, made for the run), each in their own browser context (Playwright) or API client (`cargo xtask load --people 10`):

| Scenario | What must hold |
|----------|----------------|
| Three people try to edit the same description | One gets the lock; the others see *"… is editing"*; *Edit anyway* moves the lock and keeps the first person's draft |
| Two people change the status of the same issue within a second | One wins; the other sees the conflict message; nothing is half-saved |
| A lock holder's network drops | The lock frees itself within a minute; their text is kept as a draft and offered with *Compare and save* |
| Ten people change different fields of one issue | All ten changes land (whoever was second presses *Use mine*); one event for each; the version counts up ten times |
| Ten people move issues through a workflow whose status change asks for who does the work (*Ask for*) and write an own field that Guests cannot see (M4 WP-10) | Each status that was kept is the one the issue has; a change whose buttons were read before somebody moved the issue is refused, not half saved; the Guest, who reported one issue, is told only of that issue and no notification of theirs shows the hidden field |
| Ten people add files while others change the issue | Every file that was added is stored once on its issue, none is lost or doubled |
| Changing many issues while somebody edits one of them | A lock covers only the long text, so the issue under edit changes too, and the editor's save lands afterwards with no conflict note (the status is another field); an issue whose text was saved after the preview is skipped and named, and the others change |
| Everyone drags cards on the same board | Final board matches the event log; every person's screen shows the final state after refresh |
| Timers and working hours start and stop at the same time | No double entries; working-time rules evaluated once per change |
| Searches while others change data | Results respect permissions at every moment; no errors; latency within budget |

The load run and the invariants test run against **both SQLite and PostgreSQL**; the browser scenarios of ten Playwright contexts run on SQLite only, because each worker of the end-to-end tests starts its own server on its own data folder (ADR-0023) and a PostgreSQL database for each of them is not worth what it would add: the behaviour that differs between the databases (the conditional writes of the locks, the order of events) is what the load run and the invariants test cover on both. The short version (2 minutes) runs in CI; the long version (30 minutes, mixed workload) runs nightly and checks invariants afterwards: every change has an event, no lock outlives its lease, no text is lost.

### The two ways to run them

- **Ten browsers** (`web/app/e2e/concurrent/`): each person has a browser context of their own, signed in through the API (the sign-in has its own tests). The tests read what the people see (*Saved*, the *"… is editing"* note, *Edit anyway*, the conflict note with *Use mine*, *Compare and save*), never only timing, and wait for the answer of the server or for a note on the screen, not for a fixed time. The scenarios of the table above are `iss_17_three_people_edit_one_description_and_the_first_text_is_kept`, `iss_17_a_lock_holders_network_drops_and_the_text_comes_back_with_compare_and_save`, `iss_17_two_people_change_one_status_within_a_second_and_one_of_them_is_told`, `iss_17_ten_people_change_ten_fields_of_one_issue_and_every_change_lands_once`, `iss_09_changing_many_issues_skips_the_one_changed_since_the_preview_and_names_it`, which previews a change of status for four issues, lets one editor save the text of one of them, confirms the change and reads on the screen of the person that the issue is named and left alone while the others changed with one event each, and `iss_09_changing_many_issues_changes_the_one_somebody_is_editing_and_their_text_is_saved_after`, which previews the same kind of change, lets Ben hold the lock of the description with text that is not saved, confirms the change (all four issues change, Ben's too) and has Ben save: his text lands without *Compare and save*, and his issue has one status event and one text event (the preview and the change are `previewManyChanges` and `applyManyChanges`; `web/app/e2e/support/many-changes.ts` is the one place that knows their bodies). The scenario of the dropped network says which console lines it expects (`tolerate`) from the browser of the holder, and only while that browser is offline; every other console error, every uncaught error and every other browser stays checked. `tolerate(` may only be used in `concurrent/locks.spec.ts` and in `mail-server.spec.ts` and `screenshots-notifications.spec.ts` (where the one test of a wrong mail password, and the pictures of it, expect the 502 of `mail.rejected`, without cutting the network; TEST-CONCURRENT). The lock must free within the lease (60 seconds), plus the few seconds the page takes to look again; the time the test waits is made from `leaseSeconds` and `heartbeatSeconds` of the generated constants, never from a number of its own. The lock scenarios also run in the WebKit phone project.
- **`cargo xtask load --people 10 [--minutes N | --nightly] [--database sqlite|postgres]`** (`xtask/src/load/`): the API at speed. xtask builds the program, starts the database of the run (the throwaway PostgreSQL for the second run) and runs the Node driver `web/tooling/load/main.ts`, which starts a server on the port `loadTestServer` and a data folder that xtask gave it, makes an organization (one project, six shared issues, Team members), lets the people change titles, edit descriptions under their locks (some editors vanish without letting go, some take the editing over), write comments and read, and writes what each person kept, was refused and read to a **book** (a JSON file). When the server has stopped, xtask runs `bb-load-check` on the book and the database of the run, which judges the invariants of the next section. The driver defines no invariant. Without `--database` it runs on both databases; `tools/dev/load.json` holds the defaults (ten people, two minutes, thirty for `--nightly`) and the name of the variable that carries the database address. `cargo xtask ci` runs it.
- **Against the database** (`test_concurrent_invariants_hold_after_a_run` in `bb-server`, both databases in `cargo test` under `cargo xtask db run`): ten people change four issues together over HTTP while the clock of the test runs on until the last person is done, so leases really run out (a person who types for longer than the lease waits for the clock, not for real time), and then the invariants are read from the database by the same function the load run ends in.

### Invariants after every run

They are written once, as the function `check` of the crate `bb-load-check` (`judge.rs`): the test of the server builds its book in memory and calls it, `cargo xtask load` calls it through the program `bb-load-check` with the book of the driver. Nothing else defines them (SSOT).

1. Every change has an event: the events about each issue count each version from `2` up to its version once, one event for each change that was kept (events about a lock taken over or let go count no version), and there is one event for each comment.
2. Versions only go up, one at a time: the versions of the kept changes of an issue are `2` up to its version, each once, and what one person reads of an issue never goes down.
3. No lock outlives its lease: no lock row ends later than the lease (60 seconds) from now, nobody holds a lock when the leases are over (in a load run nobody starts to edit under a lock in the last 70 seconds), and after the purge no row of a lock is left. One definition, used while the people work (the test of the server) and at the end (both).
4. No text is lost: a save that was refused (lock lost, taken over, text changed) is the draft of the person at once, the heartbeat draft of an editor who vanished is still there after the lease, and the description is the text of the last save that was kept.
5. The title is what the last kept title change set (M3-F93), and the status what the last kept status change under the workflow set (WF-01); a change that is lost or half saved is found.
6. The files of an issue are the ones that were added to it, none more and none fewer (ATT-01).
7. No notification shows what its person cannot see (SEC-06): a Guest is told only of the issues they reported, and no notification of a Guest keeps a field that is hidden from Guests, neither a built-in one that the starting role hides nor the own field the run hid. The run has nine Team members and one Guest, a project with a workflow of its own that asks for *Assigned to* on *Open* to *In progress*, and the own field *Internal note*, which Guests cannot see.

Enforced by: TEST-CONCURRENT (the scenarios, the invariants test and the load step of `cargo xtask ci` are there and not switched off), TEST-EDIT-LOCKS (the browser scenarios of the locks).

## Browser tests and the connections of the computer (M4 WP-03)

On Windows a computer that has no free ports or socket buffers left answers `net::ERR_NO_BUFFER_SPACE`, and a browser test that gets it fails (`fixtures.ts` counts every `net::ERR_*` as a defect, and no retry is added to hide it). A closed connection stays in TIME_WAIT for about two minutes, so what a run needs is the number of connections it closed in the last two minutes, not the number open. Three work folders that test at the same time share the computer.

**What a run is measured by.** The Playwright reporter `web/tooling/connection-guard.ts` looks at the connections of the computer during the run, one look after the other with a pause of a second between them (a look takes about 1.7 seconds on Windows; the next one is planned only when the one before has ended, the timer never keeps the process alive, and no look is made while the speed tests run, which measure on a computer that is otherwise idle; PowerShell's `Get-NetTCPConnection` on Windows, because `netstat` there prints the states in the language of the system; `ss` or `netstat` on Linux) and counts, for the ports of the workers' servers (`e2eWorkersFrom` to `e2eWorkersTo` of the folder's block), the connections in ESTABLISHED, TIME_WAIT and CLOSE_WAIT. At the end of the run it prints the peak, writes the second-by-second counts to `test-results/connections.csv` and fails the run when the most it saw in TIME_WAIT and CLOSE_WAIT at once is over `MOST_LEFTOVER_CONNECTIONS` (`web/tooling/connections.ts`, the one place that names the limit). The sentence names the peak, the limit, the server and the spec its worker ran last. The limit is 1,800: a run needs about 1,250, and the run before the work package peaked at 1,989, so a fall back to the old way of testing is seen. One work folder never came near the ports that Windows gives out for connections (16,384), so the failure of three merges of M3 most likely needed several folders testing at the same time, which is why the guard looks at what one run needs. The summary also says how many connections in TIME_WAIT the whole computer had (the ones with a local port of the dynamic range, from 49,152), for information; it never fails the run. The run fails too when any look failed or none was made (PowerShell, or `ss` or `netstat` on Linux, not working), so that nobody believes a guard that did not look; the summary says how many looks failed. The pure part (reading the lists, judging) is tested in `web/tooling/connections.test.ts`. Enforced by: TEST-CONNECTIONS (the reporter is in the Playwright config and fails the run, the limit is one named number, the tests of the guard are not switched off, and tests are run again only in the speed project).

**What was measured.** The full end-to-end run (about 700 tests, 16 workers, one work folder testing):

| Run | Peak in TIME_WAIT | In CLOSE_WAIT | Open at most | Where |
|-----|------------------:|--------------:|-------------:|-------|
| Before (readiness probes, one request context for each session) | 1,989 | 0 | 60 | WebKit phone |
| After the readiness wait and the shared connections of the sessions | 1,918 | 0 | 54 | `issues-new.spec.ts`, WebKit phone |
| After WebKit runs two tests at a time | 1,248 | 0 | 56 | `issues-editing.spec.ts`, WebKit phone |

Most of the connections are from **WebKit**, not from the helpers of the tests. One spec file alone shows it: `issues-new.spec.ts` leaves 16 connections in TIME_WAIT in Chromium (6 tests) and 438 in WebKit (the same 6 tests), and the project `webkit-phone` (20 tests in four files) alone peaks at 1,689, almost all of the peak of the whole run. On Windows, WebKit opens a connection for about every request of a page and closes it again (27 requests of the sign-in page leave 29 connections behind, against 2 for Chromium); the server keeps its connections alive (`curl` reuses one, and so does a Node client), so the cause is not in the listener and `crates/bb-api/src/listener.rs` is not changed. The project therefore runs two WebKit tests at a time (`WEBKIT_WORKERS`), which takes the peak from 1,918 to 1,248 and the run from 5.7 to 7.2 minutes (7.4 to 7.7 in `cargo xtask ci`).

**What each task changed.**

- *Readiness* (`web/app/e2e/support/ready.ts`): the wait for a server asks `GET /health/live` over HTTPS with pauses of 50, 100, 200 … 1,000 ms instead of a raw TCP connection every 100 ms. A question that is refused leaves no connection behind, and one that is answered leaves one. A test with a server that answers late (`web/tooling/ready.test.ts`) asks at most seven times and the server sees one connection. In the measured run this was too small to show in the peak (a start has one successful probe either way).
- *Shared connections for the sessions of the API* (`web/app/e2e/support/session-transport.ts`): every `ApiSession` and `useKey` script of a server goes over one pool of keep-alive connections of that server (closed when the server stops) and keeps the cookies of its own in a jar, so two people never share a sign-in. Before, each session was a Playwright request context with connections of its own that were closed at `dispose`. A session that was opened for a helper call is now free (`openSession` and `useKey` are no longer `async`). A connection that nobody used for 20 seconds is closed by the pool before the server's header timeout (30 seconds) would close it, and a `GET` or `HEAD` that meets a connection the server closed is sent once more; a request that changes something is never sent again, because nobody can tell whether the server took it.
- *Fewer server starts* is **not done**, and the measurement says why it would not help: a start leaves about one connection (its readiness question), a few hundred of the two thousand. A server that is reset instead of restarted needs a route that exists only in a test build, which is product code (`bb-server`, an architecture decision) and not part of this package; a fresh data folder on the same process is not possible, because the server holds its data folder open. What the package keeps is what the work package asks for first: **a spec cannot see what an earlier spec left behind**. A worker starts a server on an empty data folder for every file, and `isolation.spec.ts` proves it: it makes a project and an issue, asks the worker for the server of another file, and finds the same port with the setup code accepted again and no project in it.
- *The guard* above, and *No hiding*: no retries are added (the speed project keeps its one), and `fixtures.ts` still counts every `net::ERR_*`.
- *Showcase pictures* (M2C-F104): the browser of every window stands at the moment the sample was made (`sampleStartMs()`), so "3 days ago" is the same on every run, and the address of the invitation is fixed. Two runs of the 212 phone pictures still differ in 15 (people, the invitation link with its secret, the server status with its start time and the hash of the log, the list of sessions with its times): they show moments and secrets that the server makes. A mask for those four screens is the rest of M2C-F104.

**Reading the numbers again.** Run the end-to-end tests with `npm run test:e2e` (or `cargo xtask ci`), and read the last lines: `Connections of the tests: at most N left over at once …`. The seconds-by-seconds counts are in `test-results/connections.csv`.

## Local ports (ADR-0023)

Your machine runs other Vite projects, so Bugaboo never uses default ports. All ports live in **`tools/dev/ports.json`** (single source); Vite, Playwright, the server and xtask read them from there, and every tool uses `strictPort`, so a busy port fails with a clear message instead of silently moving.

| Offset | Used by |
|--------|---------|
| 0 | Bugaboo server in development (API + embedded app) |
| 1 | Vite dev server (hot reload) |
| 2 | Vite preview of a production build |
| 3 | Server instance for end-to-end tests (fresh sample database) |
| 4 | Vitest UI |
| 10–29 | Parallel Playwright workers, one server and database each |
| 30 | Load-test server |
| 40 | Throwaway PostgreSQL for tests (`cargo xtask db start`) |

The offsets are inside a block of 100 ports. Each work folder `bugaboo.winN` has its own block, starting at 47200 + (N − 1) · 100 (`win1` 47200–47299, `win3` 47400–47499, up to `win9` 48000–48099), so folders that build and test at the same time never share a port; any other folder uses block 1 and `BUGABOO_PORT_BLOCK` names another one. The table above shows block 1: the server of the first folder is on 47200, of the third on 47400.

The installed product asks for its port in the setup wizard (suggesting 8443 and checking that it's free); these development ports never appear in a customer installation.
