# M3 follow-ups

Points found while building M3 that were accepted for later. Each names where it will be done. The IDs (`M3-F01` …) are what the review refers to. WP-01 uses F01 and up, WP-02 F10 and up, WP-03 F20 and up, WP-04 F30 and up, WP-05 F40 and up, WP-06 F50 and up, WP-07 F60 and up, WP-08 F70 and up, WP-09 F80 and up, WP-10 F90 and up, WP-11 F100 and up.

| ID | What | Why later | Planned in |
|----|------|-----------|------------|
| M3-F01 | The eleven M3 permissions are in the catalogue (WP-01) before any route asks for them, so each is named in `tools/checks/permission-exemptions.toml` | WP-01 adds every permission with its starting values in one change, so the starting roles and the role page are right from the start; the routes come with their packages | The package that adds a permission's first route removes its line: WP-03 (`see-issues`, `make-issues`, `change-issues`, `delete-issues`, `manage-issue-types`; `change-own-issues` has no route of its own, `Evaluation::may_change_issue` judges it inside the route of `change-issues`, so its line stays), WP-04 (`edit-anyway`), WP-05 (`manage-fields`), WP-07 (`comment`), WP-08 (`move-issues`, `manage-labels`) |
| M3-F20 | The organization's default of `issues.id-mode` does not renew the IDs of existing issues; projects that follow it give their next issues the new mode, so a project can hold both kinds of IDs for a while (ADR-0021 amendment, M3 WP-03) | Renewing every project that follows the default is a big change that an administrator may not expect from a setting | WP-08 (changing many issues renews IDs the same way) or the next package that touches issue IDs |
| M3-F21 | The reader of the settings registry (`xtask/src/rust_registry.rs`) knows only written-out choices, so the choices and the default of `issues.id-mode` repeat the words of `IdMode`; a compile-time assertion stops the build when they differ | Teaching the reader to follow `Word::code()` is a change of the tool, not of this package | The next setting whose choices are the words of an enum: the reader learns to read them |
| M3-F22 | Issue types are the same everywhere, but *Manage issue types, kinds of relation and layouts* counts in projects: a project lead whose role is given on one project cannot manage the types (the check is for the whole organization) | Types per project, layouts and field levels per type come with WP-05 and WP-09 (ADR-0027) | WP-09: layouts and rules per project and type |
| M3-F23 | *Priority* is a fixed list of four words (*Low, Normal, High, Critical*), not yet an own *Pick one* field with colors and an order people can change | Own fields (WP-05) and workflows (M4) decide how built-in fields become configurable | WP-05 / M4 |
| M3-F24 | The list of issues of a project has no filter and no order but newest first: issues made in the same millisecond have no order among themselves | Search and saved filters come in M5; the issue list (WP-06) asks for what its first version needs | WP-06 and M5 |
| M3-F25 | An issue in the trash keeps its place for ever: nothing deletes it after a while, there is no screen for the trash and an issue can only be restored by its ID or key | The trash screen and the time deleted things are kept come with the issue page and the privacy work (*Remove a person*, M9) | WP-06 (Undo after a delete), M9 (keep period) |
| M3-F26 | The event of a new issue does not hold its readable ID, because the code is given out inside the change after the event was made; *History* names the issue by its internal ID | The history screen is WP-07 | WP-07 (History shows the readable ID from the issue) |
| M3-F27 | Changing the mode of issue IDs renews every issue of the project in one change; a project with tens of thousands of issues holds the change for a long time | ISS-09 says more than 1,000 issues run as a background job (WP-08); the same job can renew IDs | WP-08 (background job for many issues) |
| M3-F28 | A person can be assigned to an issue without being able to see it (no check that the person holds a role in the project) | Who may be assigned follows *Who sees people* and the roles; the issue page (WP-06) offers only people of the project | WP-06 |
| M3-F10 | Images from the hosts in `content.image-hosts` cannot be shown yet: the content security policy sends the fixed `img-src 'self' data:`, so a browser blocks them. A per-organization policy needs the header made per answer from the setting | It changes the one header table that SEC-HEADERS holds, and the cache rules of every answer; no text with an outside image exists before the issue page | WP-06 |
| M3-F11 | The preview of the editor is given no image hosts. A route that every signed-in person may read must give the list, already split with the registry's `list_items` (the browser never splits it again) | A new route needs its permission mark and its SEC-MATRIX entry; the editor is only on the frames page until the issue page uses it | WP-06 |
| M3-F12 | `SafeHtml` is made by the WebAssembly renderer only. The API client makes one for a field the server renders (a description, a comment) once such a field exists | No answer holds rendered text before issues | WP-06, WP-07 |
