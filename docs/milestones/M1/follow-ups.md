# M1 follow-ups

Points found while building M1 that were accepted for later. Each names where it will be done. Until Bugaboo tracks its own issues, this list is the issue list for M1; the IDs (`M1-F01` …) are what suppressions and TODOs refer to.

| ID | What | Why later | Planned in |
|----|------|-----------|------------|
| M1-F01 | No Windows ARM64 program (`aarch64-pc-windows-msvc`): the MSVC ARM64 build tools are not installed on the development PC, and `ring` needs them to compile its C and assembly code | Cannot be built or tested here; the target is not in `rust-toolchain.toml`, so checks do not pretend to cover it | When the "MSVC ARM64 build tools" component is installed, or on a Windows ARM64 CI runner |
| M1-F02 | The static Linux programs (x64 and ARM64, musl) are built by `cargo xtask ci` on Linux and prepared in the CI workflow, but have never run | Same reason as M0-F02: no Linux machine yet; using the runner's `gcc` for `ring` on the musl targets is untested | When the repository moves to GitHub (Linux CI runners) |
| M1-F03 | A running server renews its generated HTTPS certificate only when it starts (certificates are valid one year and renewed when under 30 days are left) | A server that runs for more than 11 months without a restart would serve an expired certificate; reloading needs a timer in the server | done in M2 WP-04: a timer looks at the certificate every hour; a generated one with under 30 days left is renewed and an own one (`tls_mode = "files"`) is read again when its files changed, both swapped into the running listener without a restart; the status page shows the end of the certificate it serves now (ACME stays with V1) |
| M1-F04 | Linting the Linux code on Windows replaces the C compiler with a no-op inside xtask (`fakecc`) for packages such as `ring` and `libsqlite3-sys`; their C code is not compiled, so only the Rust code is linted for that target | No C compiler for Linux exists on the development PC; the override is derived from `Cargo.lock`, so it follows version changes, but another crate with a C build step would need the same treatment | When another crate with a C build step is added |
| M1-F05 | The server does not yet react to Windows service control messages | The Windows service (`bugaboo service install`) comes with OPS-04 | done in M1 WP-08: the Windows service answers stop and shutdown messages and reports its state; it has only been tested as a plan, see M1-F57 |
| M1-F06 | No time limit for reading a request body or for a whole request (only for the headers, idle connections and TLS handshakes) | No endpoint reads a body yet | done in M1 WP-06: every API request has 30 seconds to finish (this also stops a body that arrives too slowly) and a body may be 1 MiB, answered as problem+json |
| M1-F07 | `cargo xtask check staged` exports the index into `target/staged-tree`; Git-based checks (secrets, file sizes) still read the real repository, and Cargo-based checks run in the export without the build cache | Exact for content; only speed differs | When staged checks become slow |
| M1-F08 | ARCH-ERRORS finds error answers built from a literal text only in the form `(StatusCode::X, "text")` | The API skeleton does not exist yet | done in M1 WP-06: ARCH-ERRORS finds error answers with a text written in the code across lines and in longer tuples, bare error statuses, and compares the generated API description with the table |
| M1-F10 | ARCH-WASM only builds `bb-core`, `bb-searchlang` and `bb-markdown` for WebAssembly; there is no size budget yet (PERF-04) | `bb-wasm` and `wasm-opt` come with the search language editor | M4 |
| M1-F11 | `#[not_personal]` cannot be used on text; a text field that is known to be harmless needs a newtype with an explicit `NotPersonal` | No such field exists yet | when the first one appears |
| M1-F12 | The generated TypeScript messages file holds the `error.*` and `setting.*` keys, so they ship to the browser | A few hundred bytes; filtering by area needs a second catalog file | M2 (app shell). Done in M2 WP-03: `cargo xtask gen messages` leaves the areas only the server and its command line show (`cli`, `config`, `cookie`, `keys`, `server`, `service`, `tls`) out of the TypeScript catalog, so a `t("config.…")` in the app is a type error; the Rust side keeps every message |
| M1-F14 | `Person` in `bb-core` is a minimal entity (id, name, e-mail, created); its table is not made yet | The accounts table comes with signing in, which decides the final fields (WP-05 made the store without it) | done in M1 WP-07: `person` and `password_login` are tables (migration 2); the fields are the ones `Person` has, plus `administrator` until roles exist (M2) |
| M1-F16 | Developer-facing `Display` texts of error types (e.g. `TlsError`) are English in code; the server shows catalogue messages instead | They never reach a person directly; a check for literal texts in Rust `Display` impls comes with the API errors | done in M1 WP-06: an error answer can only be made from an `ErrorCode`, and ARCH-ERRORS finds the ways around that, so `Display` texts of error types never reach a person |
| M1-F17 | In `check staged`, tools that look for `.git` to find the project root (rumdl) measure paths from the real repository, so path-based rules in their config see `target/staged-tree/…`; `.rumdl.toml` uses `**/` globs as a workaround | Found when the agent memory moved into the repository; a proper fix makes the export look like a project root to every path-sensitive tool | done in M1 WP-07: the staged export has an empty `.git` folder, so tools that look for it take the export as the project root; the `**/` globs in `.rumdl.toml` are gone |
| M1-F18 | ARCH-EVENTS reads the code (a command use case must call `record_change` of the `ChangeStore` port); the generated test that runs every command against the in-memory fakes and asserts the event is missing | `bb-app` has no use case and no `Ctx` yet | The first use cases (M2) |
| M1-F19 | `/health/ready` and the status page do not check the database yet (`Database::ping` exists), and `bugaboo` does not open the store, migrate or run the CLI commands `security-log verify` and `rotate-key` | The server wiring and the commands belong to setup and sign-in | done in M1 WP-08: `/health/ready` checks the database, the status page shows it, and `bugaboo security-log verify` and `rotate-key` exist (with `keys export`) |
| M1-F20 | The status page and `bugaboo security-log verify` do not show the result of `verify_security_log` yet: they should show the head (place and hash) and treat `anchored: false` on a log that has entries as a warning (nothing vouches for the end of the log) | Needs the status page and the CLI; the chain, the checkpoint and the anchor file are done | done in M1 WP-08: the status page and `security-log verify` show the head and warn when a log with entries has no anchor |
| M1-F21 | The security log keep period is not a setting yet, and no job calls `prune_security_log`; the job runner (`bb-jobs`: workers, handlers, schedules, lease extension for long jobs) does not exist, and the keep-and-delete run must also purge the payload of dead-letter jobs (it can hold personal data) after a keep period | The queue tables and the lease functions are done; the runner and the schedules come with the first job type | M4 (mail), with the keep-and-delete run (PRIV) |
| M1-F22 | Master keys have no backup or export command, and the Windows access rights of `keys/master.key` are only inherited from the owner-only `keys/` folder (on Unix the file mode is checked at every start) | A command comes with the setup and backup commands; checking a Windows ACL needs platform code | partly done in M1 WP-08: `bugaboo keys export <folder>` copies the key files and never overwrites a copy; the Windows access list is still only inherited (OPS-06 backup) |
| M1-F23 | All changes commit one after the other because the outbox counter row is locked until commit (the price of positions that never become visible out of order); SQLite has up to 8 pool connections that queue on `BEGIN IMMEDIATE` instead of one writer task with a queue | Fine for the scale target; measure with the dataset generator before changing | PERF-01…06 budgets (M3) |
| M1-F24 | Two processes that start at the same moment on a brand-new SQLite file can fail with "database is locked" while switching it to WAL mode (before the busy timeout applies); the migration lock itself is safe | A second server on the same data folder is not a supported setup; a retry on connect would hide it | done in M1 WP-08: opening a SQLite file that is being set up is retried 20 times, 100 ms apart (test reproduces it) |
| M1-F25 | The checksum of an applied migration is made from the SQL that sea-query renders for both databases; a sea-query upgrade that renders migration 1 differently would make existing databases refuse to start. A test pins the checksum, so it fails first on the developer's PC | Needs a decision when it happens (keep a list of accepted older checksums, or freeze the rendering) | The first sea-query upgrade |
| M1-F26 | The anchor file grows by one line per security-log entry and is never shortened | Lines are small (about 140 bytes); trimming must keep the newest line and be safe against a crash | With the keep-and-delete run (M1-F21) |
| M1-F27 | The per-account sign-in limit counts every attempt, not only failures, so someone who keeps trying an account name can make that account wait out the minute for everyone | A fixed per-minute window is the simplest limit that never locks for good; counting failures needs the sign-in flow | done in M1 WP-07: the limit per account counts failed tries only and a success clears it (`FailureLimits`); the limit per network still counts every try |
| M1-F28 | Rate-limit counters live in memory of one server process: a restart forgets them, and several servers behind one address would count separately | Bugaboo runs as one process in M1 | When more than one instance serves one installation (V1) |
| M1-F29 | The Vitest test of the client round-trips through a fake server (an injected `fetch`), not through the running program | Starting the program from a unit test needs the build and a port; the real browser path is covered by the Playwright tests | done in M1 WP-08: the Playwright tests drive the real program with the real client in a real browser |
| M1-F30 | Every API route shares one body limit (1 MiB) and one time limit (30 s) | No route needs more yet | M5 (attachments get their own limits) |
| M1-F31 | `openapi-typescript` needs the TypeScript 5 library, so `@bugaboo/api-client` carries TypeScript 5.9.3 next to TypeScript 7 (used by the generator only) | No release of the generator supports TypeScript 7 yet | When `openapi-typescript` supports TypeScript 7 |
| M1-F32 | The OpenAPI document does not yet name the permission of each route (`x-permission`, ARCH-PERMS) | The permission catalogue comes with `bb-policy` | M2 |
| M1-F33 | The CSRF token is not yet bound to the session: the client sends the `__Host-bb_csrf` cookie value back in `x-csrf-token`, but the server does not derive or compare it | Needs sessions | done in M1 WP-07: `csrf_check` derives the token from the session secret and compares it in constant time for every change below `/api` |
| M1-F34 | The origin check compares the `Origin` with the `Host` header of the request; behind a proxy that rewrites `Host` the public host must be passed on | Only one trusted proxy hop is supported, for the client address | When proxies that rewrite the host are supported (V1) |
| M1-F35 | When a rate-limit table is full of running counters (100,000 clients in one minute), new clients share one general counter and new sign-in keys are refused for the rest of the window; this fails closed on purpose, but an attacker with many addresses can make newcomers wait | A flood of that size needs a very large number of addresses; the first fix is simple | An aggregate counter per IPv6 /48 (or per IPv4 /24) in front of the per-client table, when public installations exist (V1) |
| M1-F36 | `webauthn-rs` is the pre-release `0.6.1-dev` (pure Rust crypto), because 0.5.5 needs OpenSSL; its `rsa` package carries RUSTSEC-2023-0071 (see the register, Accepted risks) | OpenSSL cannot be built on a plain Windows computer and would make the program depend on a C library | The first stable webauthn-rs 0.6 release |
| M1-F37 | WP-07 is only partly built: passwords, tokens, CSRF key and token, two-step codes, passkeys, e-mail rules and the sign-in tables' entities exist in `bb-auth` and `bb-core`; the use cases (`bb-app`), the tables and adapter (`bb-store`), the routes, the CSRF check, the failed-attempts-only account limit (M1-F27, M1-F33), the start-up wiring and the tests of every flow are not done | The work was handed over mid-package | done in M1 WP-07 part 2: use cases, tables, adapter, 30 routes, CSRF check, failed-tries limit, start-up wiring and the tests of every flow on both databases |
| M1-F38 | Self sign-up cannot check that an e-mail address belongs to the person until mail exists (M4); the setting help says so | No mail before M4 | M4 |
| M1-F39 | The limit per network counts every sign-in-family try (60 a minute by default) and, apart from that, failed tries (10 a window, with a success giving its try back); both use the shortened network (IPv4 `/24`, IPv6 `/48`, one definition in `NetworkPrefix`), so everybody in one `/24` shares them. The keys of a network keep a window of a minute and never grow into a long wait (many people share them); only account and person keys grow, up to 15 minutes | Telling a shared address from an attacker needs data nobody has yet | done in M1 WP-07 (review): a generous cap on all tries plus a failures-only window per network; a shared address costs only failures. The `/24` is coarse for IPv4; see M1-F49 |
| M1-F40 | A failed write of a security-log entry is only logged, it does not fail the request | Failing every sign-in while the disk is full is worse; the decision is open for review (SEC-15) | done in M2 WP-04: the decision stays (a failed entry does not refuse the sign-in). The server counts the entries it could not write since it started, and the status page warns when the count is above zero and says what to check; the status page and `bugaboo security-log verify` also name an anchor file that is ahead of the database (reason *behind*) and say what to check |
