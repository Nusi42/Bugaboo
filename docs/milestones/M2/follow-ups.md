# M2 follow-ups

Points found while building M2 that were accepted for later. Each names where it will be done. Until Bugaboo tracks its own issues, this list is the issue list for M2; the IDs (`M2-F01` …) are what suppressions and TODOs refer to.

| ID | What | Why later | Planned in |
|----|------|-----------|------------|
| M2-F01 | `Fields::project` (the `?fields=` helper) cuts only the top-level fields of an item; a view that holds an object inside (a mask inside a field) is not cut further | Every view of M2 so far is flat; the policy engine masks inside views | done in M2 WP-05: `Masked` and `mask_member` cut a view that holds a view, and the nested mask is part of the view's own type |
| M2-F02 | ARCH-LEAN's `include` rule looks only at the `items` of a paged list: it does not cover a capped list, a free-form object (an object without properties) or a schema whose name ends in `Ref` but holds more than IDs and names | No route has one of these yet, and a check for them would guess | When the first capped list embeds something, or a `Ref` schema grows beyond IDs and names |
| M2-F03 | The WebAssembly part of the first-page budget is not checked: PERF-BUNDLE measures JavaScript only | `bb-wasm` and `wasm-opt` do not exist before the search language editor (see M1-F10) | M4, with `bb-wasm` |
| M2-F04 | PERF-BUNDLE measures whatever `web/app/dist` exists on the computer: a stale build passes or fails for the code it was made from, not for the code in the working tree | `cargo xtask ci` builds the app first, so CI is exact; a local run after a code change without a build is not | When `check all` can say how old the build is, or builds it |
| M2-F05 | The start page and the other files of the app that are `no-cache` have no `ETag`, so a revalidation sends the whole file again | The start page is small and the files that matter are named by their hash | When the start page grows or a second kind of file needs revalidation |
| M2-F06 | A `401` for a session that has run out does not clear the session cookie and the browser cache (`Clear-Site-Data`); only signing out and signing out everywhere do | The person is not signed in anyway; clearing needs the answer to know that the cookie belonged to a session that ended | M2 WP-09 (access keys and sign-in by role), which touches the session answers |
| M2-F07 | A malformed `limit` (not a number) from a person who may not list is refused with `400` before the `403`, because the query is read before the handler runs | The text of the answer says nothing about the list, only that the request is not valid | When the extractors of lists judge the person first (with the policy engine, M2 WP-05) |
| M2-F08 | The browser app writes the field names of the invitations list by hand (`id,email,created_at,expires_at`) instead of taking them from the API description | The generated client has no type for the names a list can be asked for | When the API description lists the askable fields in a form the client can use |
| M2-F09 | After a real restore of the database from an older backup, the status page stays at "problem" (the anchor file reaches further than the database, reason *behind*), and there is no way to start a new anchor on purpose | A restore is the backup command's job; a new anchor must be written by the same command, after it checked the restored log (and said what was lost) | OPS-06 (M9), with the backup and restore commands |
| M2-F10 | A database password that contains an unencoded `/` or `#` is not recognised by the warning for `--database-url` on the command line (the address is read up to the first `/` after the host, so the password part is cut off) | The address form of the databases allows only encoded characters in a password (`%2F`, `%23`); a program cannot tell where a badly written password ends | When the settings take a database address in parts (host, user, password), or never: encoded addresses are what the databases accept (OPS-10) |
| M2-F11 | `/frames` and the `frames.*` messages are only a place to try the side panel, the focus view and Undo | No real screen uses the frames yet | Remove them when real screens use the frames, before the first release |
| M2-F12 | The end-to-end tests run only in Chromium | A WebKit (iPhone) project makes the suite slower and needs its own tuning | A WebKit/iPhone e2e project, M3 |
| M2-F13 | On a shared device the preferences (theme, shortcut keys, narrowed menu) stay in the browser after somebody signs out | They are kept in the browser until the settings in layers can keep them with the person | WP-07 moves them to the server |
| M2-F14 | STY-TOKENS does not find named colors (`red`) in TypeScript and may flag a `#fragment` that looks like a hex color | Rare; a stricter reading needs a real parser | When it produces a false finding |
| M2-F15 | ARCH-WEB-FEATURES checks relative imports only, not aliases or `require` | The app has no aliases | When an alias is added |
| M2-F16 | A finding of TXT-LITERAL is shown twice, also under LINT-TS (same rule) | The two checks share one configuration on purpose | When one of them can be left out of `check all` |
| M2-F17 | A person who is not an administrator and opens `/settings/…` is sent to the start page, not shown Not found | The guard is the M1 one; the permission engine decides what shows | done in M2 WP-05: the sidebar, the routes and the settings pages follow the permissions of `/auth/me` (`OnlyWith`); a person without the permission sees Not found; WP-10 adds the checks on the other routes |
| M2-F18 | Quick search, the list of shortcuts and the More sheet are in the first chunk | They are small today | Load them when first opened, when the first chunk nears its budget |
| M2-F19 | The optimistic base is captured once, so a refetch from elsewhere while changes are pending can hide new server rows or make the shown change flicker until the last change is done | Rare, and it needs pending changes to be put again on top of the refetched data | When a screen uses overlapping changes on a list that others change |
| M2-F20 | `/auth/me` carries the whole list of the person's permissions (`permissions`), an array without paging, so ARCH-LEAN has an exemption for it | The app needs the answer to show and hide places, and the list is short (the catalogue is 14 in M2) | When the catalogue grows so much that the answer should name the places instead, or when ARCH-LEAN can tell a capped list from a paged one |
| M2-F21 | `Masked` does not mask nested views unless the outer view overrides `mask`, and no check or derive enforces it: a view that holds another view with hidden fields leaks them if its author forgets | Every view of M2 is flat or masks by hand (`mask_member`, M2-F01) | M3, before the first view with a nested view of issues (a derive or a check) |
| M2-F22 | `openapi::json()` puts the extensions (`x-…`) of one object in the order of their names, which could also reorder a header or a property whose name starts with `x-` (the ordering looks at every object) | Harmless: the order of keys means nothing to a reader of the description, and it is the same on every run | When a property or header named `x-…` appears and its place in the file matters |
| M2-F23 | A role given with *its sub-projects* is checked against the sub-projects that exist when it is given (one evaluation each, inside the change, after the policy lock) and, because it reaches those made later too, against the giver's own rows that reach sub-projects (rows for the project alone do not count); a project with hundreds of sub-projects makes the change slow. **Moving is done in WP-08 too:** a move that gives somebody *Decide who has which role* above a *No access* inside the moved projects, which they could not lift before, is refused (`project.move_lifts_no_access`) and named in the preview; the preview and the rule are one function of `bb-policy` (`preview_move`), judged again inside the change after the policy lock | A project with hundreds of sub-projects still makes giving a role slow | done in M2 WP-08 (`prj_03_a_move_cannot_let_somebody_lift_a_no_access_they_are_subject_to`) |
| M2-F24 | ARCH-AUTHZ-ONLY does not catch a glob import (`use bb_policy::*`) followed by a bare `evaluate(…)` or `Inputs { … }` outside the allowed folders | No such import exists; review catches it until the check reads glob imports | done in M2 WP-10: ARCH-AUTHZ-ONLY reads every `use` of `bb_policy` (also over several lines) and refuses a star outside the policy crate, `bb-app/src/access` and `bb-store` (`bad_example_a_glob_import_of_the_policy_crate_brings_the_engine_in_unnamed`) |
| M2-F25 | The way down to a project in `GET /api/v1/projects/{project}` (`trail`) is cut at 16 steps (`truncated`), a hard cap that ARCH-LEAN has an exemption for | A tree that deep is no tree anybody walks; the cap keeps the answer small | When a tree can be deeper in practice, or when ARCH-LEAN can tell a capped list from a paged one |
| M2-F26 | The list of projects and the preview of a move read the whole tree and the rows of *Who has which role* (for one person, or for everybody) and decide in memory, so an organization with thousands of projects or assignments makes them slow | The engine decides without I/O and the tree of M2 is small; one query for each read is simpler than a decision in SQL, and the answer is paged | When a list takes long on a big sample organization (WP-13, M3), by loading only the branch a page needs, or by caching the tree per request |
| M2-F27 | The list of projects, the search, the trail, the parent references, `has_sub_projects` and the parent in the answer of a change decide what a person sees from their rows (`Policy::visible`, `shown_to`), not through `Ctx::evaluate`, so the narrowing of an access key (WP-09) does not reach any of them unless WP-09 applies it there; the preview's set of seen projects and the re-check of a move have the same gap | WP-09 is built at the same time and its narrowing is not merged | done in M2 WP-10: `Policy::visible_as` and `evaluate_as` and `Ctx::evaluation_of` take the actor's key scope, and every read of projects uses them (`auth_07_a_key_for_a_project_lists_that_project_and_below_and_nothing_else`, `auth_07_the_trail_of_a_key_stops_at_the_project_it_is_for`, and the tests of the change, the preview and the move); ARCH-AUTHZ-ONLY finds a call that skips it. What is left for the merge of WP-09: its `Actor` takes the key's scope into `Actor::key_scope`, and the two actors with a key join the matrix (`Actor::WITH_A_KEY`, the test `auth_07_access_keys_are_actors_of_the_matrix_too`) |
| M2-F28 | The preview of a move names people, not groups: *which people and groups gain or lose access* is answered by the people, whatever rows (their own or their groups') cause it | Naming a group needs *Manage groups* to see it, and the effect on people is what the person who moves has to judge | When *Who has which role* shows groups to the person who moves (WP-11), the preview can add the group behind a change |
| M2-F29 | Moving is judged for the projects the person who moves can see: a change in a project they cannot see is left out of the preview (and said so in one sentence, without a number), so they confirm a move whose whole effect they cannot read | Naming a hidden project would reveal it (UX §2.1); the refusal of a move that lifts a *No access* does not depend on what they see | Never, unless the maintainer wants a different trade: then the preview must name those changes without naming the projects |
| M2-F30 | `GET /api/v1/projects` answers a person with no role an empty list instead of refusing them, so SEC-MATRIX knows it as an exception (`FILTERS_WHAT_IS_SEEN`, `permissions_http.rs`) | The list is what the tree shows: it filters by what the person sees, and a refusal would break the sidebar for every person who has a role on one project only | done in M2 WP-10: the matrix names the exception in the table of examples (`filters_what_is_seen`), a test keeps it to this one route, and the list is checked for what each actor sees (`top_of_the_tree`) |
| M2-F31 | The sidebar narrowed to icons shows only the first page of the projects at the top, with no *Show more* | A narrow sidebar has no room for a button, and a page holds more projects than a person scans by icon | When the sidebar can be searched narrow (UX §3.1), or a person has more top projects than a page in practice |
| M2-F32 | What is open in the project tree is remembered in the browser (`localStorage`) by project ID and never cleaned up, so IDs of projects that were moved, deleted or hidden stay there | A few dozen short strings; they do nothing for a project that is not shown | When the tree state moves to the server with the other per-person settings (WP-07 layers), or when the list passes a few hundred IDs |
| M2-F60 | Six permissions have no route yet (*Decide who has which role*, *Decide what roles see*, *Check access*, *Manage people*, *Manage groups*, *Manage roles*) and are named in `tools/checks/permission-exemptions.toml` as used by the engine only | Their use cases exist (WP-05); the screens and routes are WP-11 and WP-12, and ARCH-PERMS fails an entry the day a route asks for its permission | WP-11 and WP-12: each package removes the entries of the routes it adds |
| M2-F61 | ARCH-API-OUT is a text check: `answer(…)` still takes any value, and the steps of signing in and the caller's own sign-in data answer through it, named one by one in `tools/checks/api-out-exemptions.toml` | A type that only views about the caller can take would need a marker on each of those bodies; the list of 19 names is short and kept honest (an entry that nothing needs fails) | When a second kind of entry point (MCP, M8) answers about the caller, or when the list grows |
| M2-F62 | The record of the matrix is written again by hand after a route or an actor is added (`BB_SEC_MATRIX_RECORD=write cargo xtask db run -- cargo test -p bb-server sec_01_every_route`) | The check names the command in its message, so a missing route is never silent | When a package adds a route and finds it a chore: an `xtask` command that runs it |
| M2-F63 | The part of ARCH-NO-COUNTERS that reads code knows patterns (`AUTOINCREMENT`, `count + 1`, …), not meanings: a counter that is named otherwise passes. The log position of the security log (`seq + 1`) counts up on purpose and is shown to people with *See how the server is doing* only | A check on meaning would need types for public identifiers; the patterns find the usual ways, and ADR-0021's counting issue IDs come with M3 with their folder named in `tools/checks/counter-exemptions.toml` | M3, with the counting issue IDs |
