# M2C follow-ups

Points found while cleaning up in M2C that were accepted for later. Each names where it will be done. Until Bugaboo tracks its own issues, this list is the issue list for M2C; the IDs (`M2C-F01` …) are what suppressions and TODOs refer to. Packages add lines only.

| ID | What | Why later | Planned in |
|----|------|-----------|------------|
| M2C-F01 | The message key of an error code, a permission, a topic, a starting role, a kind of people information and a field is still named by hand next to its word (`WrongCredentials => ("auth.wrong_credentials", 401, message::ERROR_AUTH_WRONG_CREDENTIALS)`); a test checks that the key follows the word (audit A13) | The key is derived from the word in one line of code, but ARCH-ERRORS and ARCH-PERMS read the table lines of `error_codes!` and `permissions!`, and TXT-CATALOG counts a key as used only when its constant or its full text is named in code; a derived key needs those three checks to read the derivation (they are `xtask`, package C-04) | C-04: let the three checks follow the rule `error.<area>.<name>`, `permission.<key>`, `starting-role.<key>`; then drop the constant from each table line |
| M2C-F02 | The values of the starting roles (permissions, field levels, *Who sees people* levels) and the permission catalogue are written in the code and in architecture §7; the tests no longer hold a third copy, they read the tables of the page, but a change of the code still needs a change of the page by hand (audit A13) | Generating the tables of a page from the code needs a generator in `xtask`, which does not depend on the product crates (it reads their source) | C-04: `cargo xtask gen` writes the three tables into the page from the source, then the tests read the page only as the check that nobody edited the generated part |
| M2C-F03 | *Where a level was set* has two shapes in the API and in the browser app: `LevelOrigin` (`set_here`, `inherited`, `role_own`, `unset`) in the tables of what roles see, and `LevelPlace` (`project`, `role_own`, `unset`) in *Check access*. The app builds both from the one `Ctx::level_place` (audit A7) | Merging them changes the API description and the web app (`bb-api` handlers, generated types, two screens), and *set here* needs the place, which *Check access* does not have | C-05 (web), together with C-03 for the handlers: one `LevelOrigin` for both screens |
| M2C-F04 | `project_choices` (a position and a number of projects skipped) and `people_to_check` (a position by name) each read the store in batches until a page is full, in two loops (audit A8) | The two continue differently (skip against position), and the loops hold a permission check that is async; a shared helper needs an async closure that fits both and would be used twice | When a third list has to be filled from batches, or C-05 if the picker is made one |
| M2C-F05 | `SettingsStore::put_setting_value`, `clear_setting_value`, `put_setting_lock` and `AuthStore::put_setting` take the key as text, and the store looks it up in the registry again (audit A17) | The check in the store is a second line of defence (ADR-0018) and its tests prove it with keys that are not in the registry; a typed key (`&SettingDefinition`) makes those tests impossible | The lead decides whether the second line of defence stays; if not, C-04 with the settings registry |
| M2C-F06 | `bb-sample` reads an ID from its text (`dump.rs`, `id_bytes`) with its own parser, next to the one of `bb_core::id` | `bb-sample` and its schema are package C-04 (B10); the parser of `bb_core::id` has no public entry for bytes from text | C-04, with the sample schema |
| M2C-F07 | `crates/bb-server/src/tests/sign_in/projects_agree.rs` still builds a tree with `Tree::new(projects.iter().map(…))`; `Tree::of(&projects)` is the one way now (audit A6) | The file belongs to the server test rigs of package C-03; changing one line there would only add to the merge | C-03, with the rigs |
