# M2C follow-ups

Points found while building M2C that were accepted for later. Each names where it will be done. The IDs (`M2C-F01` …) are what the review refers to. C-02 uses F01 and up, C-03 F20 and up, C-05 F60 and up.

| ID | What | Why later | Planned in |
|----|------|-----------|------------|
| M2C-F01 | The message key of an error code, a permission, a topic, a starting role, a kind of people information and a field is still named by hand next to its word (`WrongCredentials => ("auth.wrong_credentials", 401, message::ERROR_AUTH_WRONG_CREDENTIALS)`); a test checks that the key follows the word (audit A13) | The key is derived from the word in one line of code, but ARCH-ERRORS and ARCH-PERMS read the table lines of `error_codes!` and `permissions!`, and TXT-CATALOG counts a key as used only when its constant or its full text is named in code; a derived key needs those three checks to read the derivation (they are `xtask`, package C-04) | C-04, and it must land inside M2C: let the three checks follow the rule `error.<area>.<name>`, `permission.<key>`, `starting-role.<key>`; then drop the constant from each table line |
| M2C-F02 | The values of the starting roles (permissions, field levels, *Who sees people* levels) and the permission catalogue are written in the code and in architecture §7; the tests no longer hold a third copy, they read the tables of the page, but a change of the code still needs a change of the page by hand (audit A13) | Generating the tables of a page from the code needs a generator in `xtask`, which does not depend on the product crates (it reads their source) | C-04, and it must land inside M2C: `cargo xtask gen` writes the three tables into the page from the source, then the tests read the page only as the check that nobody edited the generated part |
| M2C-F03 | *Where a level was set* has two shapes in the API and in the browser app: `LevelOrigin` (`set_here`, `inherited`, `role_own`, `unset`) in the tables of what roles see, and `LevelPlace` (`project`, `role_own`, `unset`) in *Check access*. The app builds both from the one `Ctx::level_place` (audit A7) | Merging them changes the API description and the web app (`bb-api` handlers, generated types, two screens), and *set here* needs the place, which *Check access* does not have | C-05 (web), together with C-03 for the handlers: one `LevelOrigin` for both screens |
| M2C-F04 | `project_choices` (a position and a number of projects skipped) and `people_to_check` (a position by name) each read the store in batches until a page is full, in two loops (audit A8) | The two continue differently (skip against position), and the loops hold a permission check that is async; a shared helper needs an async closure that fits both and would be used twice | When a third list has to be filled from batches, or C-05 if the picker is made one |
| M2C-F05 | `SettingsStore::put_setting_value`, `clear_setting_value`, `put_setting_lock` and `AuthStore::put_setting` take the key as text, and the store looks it up in the registry again (audit A17) | The check in the store is a second line of defence (ADR-0018) and its tests prove it with keys that are not in the registry; a typed key (`&SettingDefinition`) makes those tests impossible | Closed by the lead: the store keeps taking the key as text as its second line of defence (ADR-0018), so `put_setting_value(key: &str)` stays and nothing is planned |
| M2C-F06 | `bb-sample` reads an ID from its text (`dump.rs`, `id_bytes`) with its own parser, next to the one of `bb_core::id` | `bb-sample` and its schema are package C-04 (B10); the parser of `bb_core::id` has no public entry for bytes from text | C-04, with the sample schema |
| M2C-F08 | `crates/bb-sample/src/roster.rs` (line 40) has its own hand-written `Role` enum for the starting roles of the sample organization, next to `StartingRole` of `bb-policy` (audit B10) | `bb-sample` and its schema are package C-04 | C-04: use `StartingRole` and drop the copy |
| M2C-F09 | `roles::levels` (line 136) checks the level of the project itself before the policy lock is taken; the check inside the change covers the projects below it only. A role change that lands between the two can be judged on the old state (an old race, not new in C-02) | The fix moves the check into the change after the lock, which changes the order of the refusals the tests pin down | C-04, or the first package that touches `roles/levels.rs` again |
| M2C-F10 | ARCH-PERMS counts the `Name =>` lines of the catalogue file; the words of topic, counts and kind had to move to `parts.rs` so that they are not counted (C-02) | The check should read only the `permissions!` block; then `parts.rs` is not needed for line counting | C-04, with the other checks of F01 |
| M2C-F20 | The test of `bb-store` (`crates/bb-store/src/tests/access_keys.rs`) still has its own `type Failure = Box<dyn std::error::Error + Send + Sync>` next to `bb_testing::Failure` (audit B8) | C-02 refactors `bb-store` at the same time and owns its files; a one-line change there would only add a merge conflict | after C-02 is merged: use `bb_testing::Failure` (one line) |
| M2C-F21 | The failure limit that never limits is written twice: `NoLimit` in the `bb-app` tests (`crates/bb-app/src/tests/world.rs`) and `Unlimited` in `bb-sample` (`crates/bb-sample/src/limits.rs`) (audit B11) | The one home is `bb-app` (the trait `FailureLimit` lives there), which C-02 owns | after C-02 is merged: one `NoFailureLimit` in `bb-app`, used by both |
| M2C-F22 | The test passwords `PASSWORD` and `OTHER_PASSWORD` are defined in `bb-app` (`tests/world.rs`) and in the sign-in rig of `bb-server` (`tests/sign_in/rig.rs`) | A shared home (`bb-testing`) needs a dev-dependency in `bb-app`, a crate C-02 owns | after C-02 is merged: define them once in `bb-testing` |
| M2C-F24 | `operations()` does not list an HTTP `QUERY` operation (`PathItem::query` of utoipa): `http::Method` has no constant for it and no route uses it | Nothing to walk today; adding it blind would be dead code | the first `QUERY` route: add it to `each_operation` in `crates/bb-api/src/openapi.rs` |
| M2C-F26 | The helpers `inviter`, `role_with`, `checker` and `switch` of the server tests take `two_step: bool` (audit B12, boolean flags) | The flag is the value of the field `two_step` of the use cases `MakeRole` and `ChangeRole` that they fill in, not a switch between behaviours; audit B12 is C-04's | C-04 decides whether a name for the switch is worth it |
| M2C-F60 | The preview of *Who sees people* (`PeoplePreview.tsx`) names a person whose level is *Hidden* as *Someone* with a capital in every place of the sentence, also in the middle (*"… is assigned to Someone"*); the other names use the form for the middle of a sentence (`access.person-someone-inside`, *someone*). Kept as it was in C-05, which changes no text | A fix changes the sentence people read; C-05 adds no feature and changes no visible text | The maintainer decides the wording; then `someoneName(position)` already has both forms |
| M2C-F61 | The generator writes no list of permission keys for the browser: the type `PermissionKey` is the union of the API description (`Schema<"Permission">`), which is all the screens need, and the one place that wants every key (the topics of *Organization settings*) now takes them from its children | A runtime list would be used by no code | When a screen has to list every permission without asking the server: write it from the `Permission` enum of the API description in `gen api` |
| M2C-F62 | The two shapes of *where a level was set* (`LevelOrigin`, `LevelPlace`, see M2C-F03) are still two in the API and in the browser app | The browser can only follow the API: the change starts in the handlers and the API description of `bb-api` (C-03 is merged without it), and C-05 is the web part | A package that touches the handlers of the level tables: one `LevelOrigin`, then the web part |
| M2C-F63 | Some components still take a boolean that is a state of the screen and not a choice between looks: `Sidebar` (`narrow`, `inDrawer`, `locked`), `NavLink` and `NavButton` (`narrow`), `UndoHost` (`aboveBar`), `Button` (`wide`), `SubmitButton` (`wide`) | They are independent switches of the layout, not several flags for one choice; a prop with one word each would be the same flag | The theme file (C-06) turns them into `data-state` and `data-variant` |
